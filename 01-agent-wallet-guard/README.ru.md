# 01 — agent-wallet-guard

_English version: [README.md](README.md)_

**Сторож расходов на LLM API: измеряет *факт*, находит *сессию-виновника*, оповещает только когда что-то не так.**

Это модуль 01 в серии скриптов, которые появились, когда я стал держать дома личного ИИ-агента. Агента зовут **Hermes** — он живёт на моём сервере, работает круглосуточно, ведёт свою рутину (дайджесты, наблюдение за ценами, здоровье, мониторинг собственных сбоев) и пишет скрипты, которые ему нужны. Каждая папка в этом репозитории — один такой скрипт: одна решённая проблема и инструмент, который её решил.

Несколько слов для тех, кто раньше с этим углом стека не сталкивался. **LLM** — это *Large Language Model*, большая языковая модель: ИИ, которому я плачу за ответ текстом. Провайдер берёт плату за **токены** (токен — это примерно слово или его часть) и видит за каждым моим обращением **сессию** — один непрерывный разговор. **Задание по расписанию** (по-английски **cron job**) — это задача, которая срабатывает по таймеру — здесь, каждые 30 минут — без моего участия. Сторож из этой папки — именно такое задание: он измеряет реальный баланс у провайдера, называет сессию, которая наносит основной ущерб, и подаёт голос только когда что-то действительно не так.

Скрипт — `agent_wallet_guard.py`. Соседний файл `guard_config.example.env` перечисляет каждую настройку с комментариями. Логика из этой папки работала каждые 30 минут в продакшене неделями, прежде чем я её сложил в репозиторий.

## Зачем это сделано

Дашборд провайдера показывает итоги — сколько я потратил сегодня, на этой неделе, в этом месяце. Он *не показывает*, какая именно сессия съела деньги. Я узнал об этом на собственной шкуре: одна огромная сессия тихо съела неделю моего бюджета. **Контекст** — рабочая история разговора, которую модель перечитывает на каждом ходу — вырос до нескольких сотен тысяч токенов, и агент прогонял его заново на каждом шаге. Поверх этого — **попытки сжатия**, на которых ассистент пытается сжать длинный разговор в короткое резюме, — зависали на 6–24 минуты и уходили в повтор; каждая такая повторная попытка — это платный вспомогательный вызов у основного провайдера по полной цене. Зависшее сжатие — не «поставленная на паузу» система, а тихо работающий счётчик.

Мои собственные оценки из таблиц цен на токены были ошибочны дважды. Цена **выходных токенов** дрейфует примерно в 2 раза за время, так что число в конфиге редко совпадало с числом в реальном инвойсе. А входная сторона тоже выглядит не так, как кажется: когда тот же префикс промпта отправляется повторно, большинство провайдеров считают это **попаданием в кэш** и берут за это в **1/50–1/100 от цены свежего входа**. В реальном трафике агента, где длинная история сессии отправляется заново на каждом ходу, именно этот вход из кэша и определяет счёт.

Единственное честное число — это баланс, который сам провайдер отдаёт через API аккаунта. Единственное полезное оповещение — то, которое называет сессию: чтобы я мог пойти, посмотреть и при необходимости сбросить. Всё остальное в этой папке вытекает из этих двух фактов.

## Как это работает

1. **Зафиксировать реальный баланс**, который отдаёт провайдер, на первом измерении каждых суток по UTC. Всё остальное — дельта от этого якоря.
2. Если было пополнение, скрипт замечает, что баланс *вырос*, и переставляет якорь на новое значение. Пополнение — не расход.
3. **Расход = якорь − текущий баланс.** Когда расход переваливает за суточный порог, скрипт запрашивает у базы использования сессию с самым большим потреблением кэш-токенов за сегодня и называет её кандидатом на виновника.
4. **Сетевой сбой — не оповещение.** Если API провайдера лёг или мой запрос завис по таймауту, скрипт молчит и ждёт следующего тика.

Оповещения троттлятся, чтобы меня не будили в три часа ночи по одному и тому же поводу дважды подряд: оповещение о низком балансе — не чаще раза в 12 часов; оповещение о суточном расходе — не чаще раза в 4 часа. В каждом оповещении сверху указывается сессия с самым большим потреблением кэш-токенов — потому что в этой схеме именно сессия, прогоняющая сотни тысяч токенов на каждом ходу, двигает стрелку. Здоровый случай — самая громкая часть конструкции: скрипт не печатает ничего, значит слать нечего, значит канал доставки молчит. Пустой stdout — это успех.

## Быстрый старт

Моя интеграция с планировщиком — это и есть всё развёртывание:

```
scheduler: every 30m, no LLM agent, stdout is delivered verbatim
```

— скрипт *и есть* задание. Раз в 30 минут он запускается, и пустой stdout не отправляет ничего.

Минимум, который нужно задать:

```bash
WALLET_BALANCE_URL=https://api.deepseek.com/user/balance
WALLET_API_KEY=sk-...                  # либо WALLET_API_KEY_ENV=DEEPSEEK_API_KEY
WALLET_LOW_BALANCE=2.0                 # порог в USD (по умолчанию 2.0)
WALLET_DAILY_BURN=1.5                  # суточный расход в USD (по умолчанию 1.5)
```

Чтобы получить строку **с виновником**, нужно указать скрипту на базу sqlite с таблицей `session_model_usage` (колонки: `session_id, billing_provider, first_seen, cache_read_tokens, input_tokens, output_tokens, reasoning_tokens, api_call_count`):

```bash
WALLET_USAGE_DB=/var/lib/agent/state.db
WALLET_PROVIDER=deepseek               # значение billing_provider для фильтра
```

Состояние — суточный якорь и временные метки последних оповещений — лежит в небольшом JSON-файле, по умолчанию `~/.cache/agent_wallet_guard.json`. Скрипт создаёт каталог при первой записи, так что руками ничего делать не надо. Внутренний порог, по которому сессия помечается как «кандидат-монстр», — 40 миллионов кэш-токенов за одни сутки по UTC. Сетевой сбой молчит по дизайну — если провайдер лежит шесть часов, скрипт мне не скажет, потому что мне нужны оповещения о *моей* проблеме, а не о проблемах провайдера.
