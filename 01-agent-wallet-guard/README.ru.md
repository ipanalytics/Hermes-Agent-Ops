# 01 — agent-wallet-guard

**Watchdog для расходов на LLM API: измеряет *факт*, находит *сессию-виновника*, оповещает только когда что-то не так.**

## Что вы получаете

- `agent_wallet_guard.py` — production-watchdog (именно эта логика работал каждые 30 мин на протяжении недель). При нормальной работе stdout пуст; прореженные (throttled) оповещения на: низкий баланс (1 раз/12 ч) и дневное выгорание выше порога (1 раз/4 ч), каждое — с сессией-лидером по токенам чтения кэша как кандидатом в виновники.
- `guard_config.example.env` — каждый параметр настройки, с комментариями.

## Проблема

Дашборды провайдера показывают суммы, но не *какая сессия* сожгла деньги. Одна гигантская сессия способна молча съесть недельный бюджет: контекст в несколько сотен тысяч (K) токенов, проигрываемый заново на каждом ходе, плюс **попытки сжатия, которые висят 6–24 минуты и повторяются бесконечно** — каждый повтор это платный вспомогательный (aux) вызов к основному провайдеру. Наивные оценки по таблицам цен токенов ошибаются дважды: цены на выход (output) дрейфуют в ~2 раза, а вход по попаданию в кэш (~50–100x дешевле свежего) доминирует в реальном трафике агентов.

## Принцип работы

1. **Заякоривание на реальном балансе** из API провайдера при первом измерении каждых UTC-суток.
2. Пополнение переустанавливает якорь (дозаливка средств — не «выгорание»).
3. Выгорание = якорь − текущий баланс. При пересечении порога запросить в БД учёта использования самую прожорливую сессию дня и назвать её.
4. Сетевой сбой → молчать. Интеграция с планировщиком: запуск каждые 30 мин, пустой stdout ничего не отправляет.

## Подключение к cron (как это запускаем у нас)

`scheduler: every 30m, no LLM agent, stdout is delivered verbatim` — скрипт *и есть* задача.
