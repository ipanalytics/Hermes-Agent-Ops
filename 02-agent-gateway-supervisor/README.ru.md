# 02 — agent-gateway-supervisor

**Корректный надзор за шлюзом: systemd владеет процессами, один внешний супервизор обнаруживает состояния «живой, но мёртвый», а разрешение polkit позволяет непривилегированному агенту перезапускать собственные юниты. Никаких `gateway restart` изнутри агента, никогда.**

Ревизия 2026-09-07: переработано после инцидента, в котором старая конструкция (самописный watchdog + `hermes gateway restart`, конкурирующий с systemd) повредила БД состояния и уронила весь агент примерно на ~12 ч. Урок закреплён в приведённой ниже структуре файлов.

## Файлы

| Путь | Что это |
|---|---|
| `systemd/gateway.service` | системный юнит для шлюза обмена сообщениями. `Restart=on-failure`, `RestartSec=10s`, `StartLimitIntervalSec=300/StartLimitBurst=5`, `NoNewPrivileges=true`, изолированные пути. |
| `systemd/dashboard.service` | системный юнит для приватной веб-панели (то же усиление безопасности). |
| `gateway_supervisor.py` | внешний демон-супервизор (запускается как **пользовательский** юнит, а не как задание cron — см. ниже). Обнаруживает: устаревший heartbeat, маркеры `deleted state.db-wal`, свежие строки "session storage could not be written" / "unable to open database file" в логах шлюза (≥2 за 4 мин). Перезапускает юниты через `systemctl` с периодом охлаждения и почасовым лимитом (3/ч → эскалация к «требуется ручное восстановление», никогда не восстанавливает состояние автоматически). Дедуплицированные оповещения: одно сообщение на переход состояния (проблема / восстановление), а не на цикл опроса. |
| `systemd/supervisor.service` | пользовательский юнит (`systemctl --user`), который запускает `gateway_supervisor.py --supervise`. **Почему пользовательский юнит вместо cron-стража:** каждый предыдущий страж жил внутри собственного cron-планировщика шлюза — циклическая зависимость (шлюз умирает → cron умирает → ничего не воскрешает шлюз). systemd независимо воскрешает супервизор (`Restart=on-failure`), а linger поддерживает пользовательские юниты живыми после перезагрузок. |
| `polkit/49-mynet-hermes.rules` | позволяет пользователю `hermes` выполнять `systemctl restart/start` для двух юнитов. Без этого: `Access denied` (sudo недоступен при `NoNewPrivileges`). Устанавливать от root в `/etc/polkit-1/rules.d/`. |
| `scripts/hermes-update-run.sh` | *единственный* санкционированный процесс обновления: приостановить супервизор → `systemctl stop dashboard` → `hermes update --yes` → `systemctl restart gateway` + `systemctl start dashboard` → проверка heartbeat/юнитов → отчёт ✅/❌. Сначала останавливает веб-панель, потому что инструмент обновления считает запущенную веб-панель "manual-serve" и перезапустил бы её в преходящем cron scope (изначальный источник двойного управления). |

## Эксплуатационные правила

1. **Один владелец на процесс.** Шлюз одновременно управлялся systemd *и* самописным watchdog, выполнявшим `hermes gateway restart`. Результат: "Gateway already running (PID …)" → systemd завершился ошибкой после 8 попыток, а зависший `hermes gateway restart` удерживал `state.db`/`-wal`/`-shm` открытыми через несколько файловых дескрипторов, поэтому новые сессии не могли записывать. Мониторинг и перезапуски выполняются **только** через `systemctl`.
2. **`hermes gateway restart` запрещён для супервизоров.** Если БД была подменена под живыми процессами, Hermes останавливает записи и перенаправляет сообщения в `sessions/*.jsonl` + `pending_messages/`; сама БД может оказаться `malformed`. Робот, перезапускающий компоненты, не исправляет это — он ухудшает ситуацию. Вместо этого супервизор эскалирует.
3. **Юнит в состоянии "up" всё ещё может быть мёртвым.** `systemctl is-active` недостаточно: признаки сбоя были в хвостах логов ("session storage could not be written"), тогда как процесс работал нормально. Следите за heartbeat и свежими маркерами отказа записи, а не только за состоянием процесса.
4. **Следите за наблюдателем без cron.** Любой супервизор, чьё воскрешение зависит от собственного планировщика шлюза, — фикция. Пользовательский юнит systemd + linger — надёжный ответ.
5. **Оповещать о переходах, а не о циклах.** Наблюдатель, который отправляет сообщение на каждый опрос, превращает 2-часовой сбой в ~200 сообщений (наблюдалось). Одно оповещение "down" + одно оповещение "recovered" на инцидент, с ограничением напоминаний в 30 мин.
6. **Файл паузы.** `touch <state>/gateway_watchdog.paused` перед ручным обслуживанием (обновления, восстановления). Устаревшая пауза (старше ~3 мин, обновление не выполняется) снимается супервизором с оповещением.
7. **Эскалация, никогда не авто-восстановление.** После превышения почасового лимита перезапусков супервизор останавливается и просит человека восстановить БД из резервной копии — робот не должен самостоятельно откатывать состояние.

## Обнаруживаемые классы сбоев

- Heartbeat устарел (>5 мин) — процесс мёртв или завис.
- `deleted state.db-wal` в логах — файл БД был подменён под живым процессом.
- Свежие строки отказа записи за последние минуты — хранилище сессий сломано, хотя процесс выглядит здоровым.

## Окружение

`gateway_supervisor.py` читает `OPS_CHAT_ID` / `OPS_THREAD_ID` для оповещений (задаётся в `Environment` юнита или в `.env` шлюза). Токены читаются из окружения во время выполнения — ничего не зашито.
