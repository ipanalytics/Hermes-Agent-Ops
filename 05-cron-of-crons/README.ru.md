# 05 — cron-of-crons

**Самонаблюдающиеся задачи по расписанию: операторский обход, проверки свежести и цепочка «кто следит за кем».**

## Что вы получаете

- `operator_prompt.example.md` — бриф ежедневного обхода: самодостаточный, экономный, формат вывода (одна строка при норме, ⚠️/🔴 на каждый инцидент), дедупликация за счёт преемственности, **свежесть с учётом расписания**, намеренные исключения.
- `watch-table.md` — матрица «кто следит за кем» + анализ выживаемости (что переживает перезапуск шлюза) + правило: каждый наблюдающий контролируется другим слоем, который его переживает.
- `delivery-policy.md` — таблица решений «локально vs топик vs алерт»; запуски LLM, пропускаемые через мониторинг (monitor-gated); паттерн watchdog при пустом stdout.

## Проблема

Запланированные LLM-задачи дрейфуют: ошибка доставки, молча пропущенный день, задача, привязанная к мёртвой модели, проверка свежести, которая не знает о существовании выходных. Если ничто не следит за следящими, вы узнаёте об этом с опозданием на неделю.

## Паттерны (кратко)

### Операторский обход (ежедневно)

Проверяет: задачи включены? ошибки доставки/срабатывания? здоровье (диск/ОЗУ/зомби-процессы)? **свежесть по реальному расписанию каждой задачи**? гигиена артефактов? Отчёт: норма → одна строка; инциденты → построчно; нет изменений → "no change". Запускается на *другой* модели, нежели задачи, которые он проверяет. Некоторые домены намеренно исключены из-под надзора — это задокументировано, а не недосмотр.

### Цепочка «кто следит за кем»

cron → скрипт → внешний демон → сторожевой cron. Каждый слой контролируется *другим* слоем, который переживает контролируемый им объект. Никакого самореферентного восстановления.

### Дисциплина доставки

Сборщики данных доставляют локально (никогда не пишут пользователю); настоящие алерты уходят в топик; одноразовые напоминания — задачи с фиксированным текстом и без агента, которые отключаются сами.
