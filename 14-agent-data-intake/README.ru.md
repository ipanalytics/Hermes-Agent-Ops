**Небольшой постоянно работающий сервис, который принимает показания от устройств — BLE-манжету (тонометр, подключённый по Bluetooth), приложение на телефоне, любой источник, который умеет отправить JSON по HTTPS-адресу — и сохраняет их в локальный SQLite-файл. Приёмник — собственный systemd user unit, а не задание в планировщике шлюза (cron). Он многопоточный: один медленный клиент не может заклинить весь процесс. Сторона устройства не доверяет сети: каждое измерение сначала ложится в локальный spool-файл, и переименовывается в `*.delivered` только тогда, когда POST вернул 200. Источник истины — spool, а не сеть.**

Редакция 2026-09-07. Повод — инцидент, в котором приёмник умер за ночь, а моё утреннее измерение пришло **на двенадцать часов позже — но не потерялось**: spool на стороне устройства его удержал и выгрузил, как только приёмник вернулся в строй.

## Какую задачу решает эта папка

Hermes, мой домашний агент, живёт на моём сервере. Часть того, что ему нужно снаружи, приходит от устройств, которые я ношу или держу рядом: BLE-манжета с моими цифрами давления, приложение на телефоне с весом или оценкой сна, IoT-датчик, который что-то сообщает каждую минуту. Устройство не умеет говорить с базой данных напрямую — ему нужно послать данные *куда-то* на сервер. Этим «куда-то» служит крошечный HTTP-приёмник, его ещё называют webhook: устройство шлёт JSON по адресу, приёмник проверяет общий токен, и показание дописывается в маленький SQLite-файл, который дальше читает уже сам агент.

Три вещи убивают такой приёмник незаметно, и каждая стоит мне реального измерения:

1. **Приёмник запускается планировщиком шлюза.** Шлюз — это долгоживущий процесс, внутри которого живёт агент. Его планировщик запускает задачи по расписанию (cron-style). Когда шлюз перезапускается из-за обновления, всё, что он породил, умирает вместе с ним — а cron-овский watchdog (маленький скрипт, который периодически проверяет «жив ли приёмник, и если нет — запускает его») тут не поможет, потому что он сам и был тем, что умерло. Cron-овский watchdog — не спасательный круг для того, что должно переживать шлюз.
2. **Приёмник однопоточный.** Самые простые HTTP-серверы из стандартной библиотеки Python обрабатывают по одному запросу за раз. Если один клиент подключился и завис — нестабильный мобильный канал, медленное тело запроса — все последующие запросы встают за ним в очередь, включая тот самый ping, на который опирается watchdog. Watchdog видит «нет ответа», решает, что приёмник сломан, и убивает процесс, который всего лишь застрял за одним клиентом. Отказ «жив, но мёртв» бывает не только у шлюзов — у приёмных серверов тоже.
3. **Устройство доверяет сети.** Устройство отправило POST и не получило ответа — измерение забыто. Я измерил в 05:08, приёмник был недоступен до 15:15, и утреннее число просто никогда не пришло. Чинить тут надо не скорость сети, а очередь, которая живёт на стороне устройства.

В этой папке лежат четыре куска, которые чинят все три причины разом: собственный systemd user unit с собственной политикой перезапуска, многопоточный приёмник (~120 строк stdlib), небольшой многопоточный TLS-прокси для публичного endpoint, и контракт очереди, который должен поставлять каждый отправитель на стороне устройства.

## Файлы

| Путь | Что это |
|---|---|
| `systemd/webhook.service` | Пользовательский unit (`systemctl --user`) для HTTP-приёмника. `Restart=on-failure`, `RestartSec=5s`, логи в постоянный путь под `~/.local/state/intake/`. Unit включён с `linger`, поэтому переживает перезагрузки и не зависит от шлюза. |
| `systemd/tls-proxy.service` | Пользовательский unit для небольшого многопоточного TLS-прокси перед приёмником, когда endpoint публичный (`:8899 TLS → :8443 HTTP`). Та же политика перезапуска. Сертификаты берутся из **постоянного** каталога, никогда из `/tmp`. |
| `webhook_receiver.py` | Минимальный однофайловый приёмник. `ThreadingHTTPServer`, проверка общего токена (заголовок HTTP `Authorization` или `?token=` в query), запись в SQLite и три endpoint: `POST /webhook` для записи, `GET /ping` для watchdog, `GET /last` для отладки. ~120 строк, только стандартная библиотека Python. |
| `device_side/queue_pattern.py` | Контракт стороны устройства в коде: сначала записывать каждое измерение в spool-файл (`spool/recYYYYMMDDTHHMMSSffffffZ.json`), потом POST; при сбое повторять попытку каждый цикл, без предела; переименовывать в `*.delivered` только после HTTP-успеха. При старте скрипт ещё выгружает всё, что остался от прошлого запуска (`spool/*.json` → `*.delivered`). Только stdlib. |

Несколько слов о полях базы — от них зависит, что агент сможет прочитать потом: `metrics(id, ts, metric, value, unit, systolic, diastolic, source, received_at)`. `ts` — это когда устройство говорит, что измерение произошло; `received_at` — когда строка реально легла. Оба важны: они позволяют отличить «утром измерения не было» от «строка просто пришла позже».

## Почему я делаю это именно так

1. **Приёмник — инфраструктура, а не функция агента.** Он живёт отдельным systemd user unit с собственной политикой перезапуска. Пока он сидел внутри мира шлюза, один отказ шлюза уронил и приём данных — моё утреннее измерение пролежало в очереди 12 часов, прежде чем приёмник вернулся. Паттерн unit-модуля — тот же, что в 02 (agent-gateway-supervisor) для самого шлюза: всё, что должно переживать шлюз, нуждается в политике перезапуска, которой шлюз не владеет.
2. **Один зависший клиент не должен уметь убить сервер.** Однопоточные серверы из стандартной библиотеки Python заклинивают на зависшем соединении: перестаёт отвечать весь процесс, включая собственный `/ping`. Поэтому приёмник работает на `ThreadingHTTPServer` (а TLS-прокси — на многопоточном сокет-сервере). У watchdog появляется настоящий сигнал, а не ложный.
3. **Логам и сертификатам не место в `/tmp`.** `/tmp` чистится при перезагрузке; приёмник, у которого TLS-сертификат лежит там, умирает в худший возможный момент — утром, при измерении. Unit-файлы пишут логи в `~/.local/state/intake/`, а сертификаты живут в постоянном каталоге, которым я управляю.
4. **Никогда не терять измерение из-за сети.** Сторона устройства сначала пишет локально (`spool/*.json`), потом POST; файл помечается доставленным только по HTTP-успеху. При сбое — повтор каждый цикл, без предела. Источник истины — очередь; сеть — лишь способ доставки. Приёмник может лежать хоть двенадцать часов: измерение переживёт и придёт, когда тот вернётся.
5. **Сканировать непрерывно, а не по расписанию.** BLE-наблюдатель, сканирующий «5:10–5:20», пропустит меня, измеряющего в 5:08. Постоянно работающий цикл сканирования (12 с сканирование, 5 с пауза ≈ 17 с цикл) ловит любой всплеск advertisement-пакетов длиннее цикла — на production 6 перехватов из 6. Я не прошу пользователя подстраиваться под окно.
6. **Health check — реальный запрос, а не проверка порта.** `ss -tln` показывает порты «listening» и у заклинившего процесса. Watchdog HTTP-ping'ает приёмник (`GET /ping`, ожидаем 200 за несколько секунд). Это единственный сигнал, который отличает «жив» от «слушает».
7. **Проверка цепочки целиком, без устройства.** Я POST'лю одно синтетическое измерение с настоящим токеном через TLS-прокси и смотрю, что строка легла в SQLite; потом удаляю её. Так проверяется путь приёмник → БД до того, как начнётся отладка BLE — а устройство при этом может быть где угодно.
8. **Оповещать о переходах состояния, а не при каждом опросе.** Watchdog на стороне VM/устройства проверяет приёмник каждые пять минут, но алерт шлёт один раз за инцидент (состояние хранится в файле) и не чаще раза в тридцать минут — не на каждом опросе. Двухчасовой отказ даёт ~2 сообщения, а не ~24.

## Что лежит в файле токена

Приёмник сам генерирует себе токен при первом запуске и кладёт его в `~/.local/state/intake/token.txt` с правами `0600`. В unit-файле явно задан `HOME=/home/USER`, потому что `os.path.expanduser("~")` внутри systemd user unit без этого не работает: у unit нет логина, и домашний каталог пуст, пока его не передали явно. Общий токен может прийти в одном из трёх мест: заголовок `X-Health-Token`, заголовок HTTP `Authorization` (в формате, который большинство HTTP-клиентов используют для передачи токенов), или query-параметр `?token=…` в URL. Ни одно из них не переопределяет файл токена: файл — источник истины, запрос — просто способ его передать.

## Хронология отказа (наблюдавшаяся)

```
02:00  приёмник умирает (застрявший клиент; убит чужой цепочкой перезапуска)
05:08  я измеряю; BLE-демон устройства получает измерение (24/7 сканирование)
05:08  POST не проходит (connection refused) → измерение уходит в spool, повтор каждые ~17 с
05:08–15:15  повторы проваливаются; перезапускать приёмник некому (cron-спасатель тоже мёртв)
15:15  unit приёмника стартует в новой архитектуре; первый повтор успешен → доставлено
15:15  spool выгружен, *.delivered переименованы; утреннее измерение целым ложится в SQLite
```

Полные потери: **ноль измерений**. Задержка: 12 часов, целиком из-за отсутствующей политики перезапуска — того самого исправления, которое этот модуль и поставляет.

## Тестирование без устройства

```bash
# имитация устройства: POST одного измерения через TLS-прокси
curl -sk -X POST https://intake.example:8899/health/webhook \
  -H "X-Health-Token: $(cat /path/to/token_file)" \
  -H "Content-Type: application/json" \
  -d '{"source":"test","metrics":[{"metric":"heart_rate","value":60}]}'
# → {"status":"ok","stored":1}; затем удалить строку в SQLite.
```

Этот единственный round-trip покрывает весь путь снаружи приёмника до базы данных, с настоящим токеном и настоящим TLS-слоем. Если он работает, отладка BLE стартует от известной исправной базы; если не работает — проблема в приёмнике, а не в радио.
