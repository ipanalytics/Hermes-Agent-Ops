# 14 — agent-data-intake

**Надёжный приём данных от устройств к агенту: BLE-устройства, ретрансляторы на телефоне и любые источники, отправляющие данные через webhook. Приёмник — это пользовательский unit systemd (не cron шлюза); он многопоточный, поэтому один зависший клиент не может его убить; сторона устройства никогда не доверяет сети — она ставит данные в spool и повторяет отправку до успешной доставки.**

Редакция от 2026-09-07, после инцидента, в котором приёмник данных умер за ночь, а утреннее измерение показателей здоровья пришло **с опозданием на 12 часов — но не потерялось**: очередь на стороне устройства удержала его и выгрузила, когда приёмник вернулся в строй.

## Класс отказов, который обрабатывает этот модуль

Устройство (BLE-манжета, приложение на телефоне, IoT-датчик) отправляет измерения на приёмник webhook. Приёмник — небольшой постоянно работающий процесс. Три вещи убивают его незаметно:

1. **Приёмник зависит от cron шлюза агента, чтобы оставаться живым.** Шлюз умирает → cron умирает → никто не перезапускает приёмник → все измерения с этого момента падают. Watchdog на основе cron — *не* спасательный круг ни для чего, что должно переживать шлюз.
2. **Приёмник однопоточный.** Один клиент, который подключился и завис (нестабильный мобильный канал, медленное тело запроса), блокирует все последующие запросы — включая health-check ping, — поэтому watchdog видит «down» и убивает процесс, который просто застрял за этим клиентом.
3. **Устройство доверяет сети.** Если POST не проходит, измерение потеряно — пользователь измерил в 05:08, приёмник был недоступен до 15:15, и утреннее число просто никогда не приходит.

## Файлы

| Путь | Что это |
|---|---|
| `systemd/webhook.service` | пользовательский unit (`systemctl --user`) для HTTP-приёмника. `Restart=on-failure`, `RestartSec=5s`, логи в постоянный путь. Linger сохраняет пользовательские units живыми между перезагрузками. |
| `systemd/tls-proxy.service` | пользовательский unit для небольшого многопоточного TLS-прокси перед приёмником, когда endpoint публичный (`:8899 TLS → :8443 HTTP`). Та же политика перезапуска. Сертификаты берутся из **постоянного** каталога, никогда из `/tmp`. |
| `webhook_receiver.py` | минимальный однофайловый приёмник: `ThreadingHTTPServer`, проверка общего токена (header/query), добавление в SQLite. ~100 строк, только stdlib. |
| `device_side/queue_pattern.py` | контракт стороны устройства в коде: сначала записывать каждое измерение в spool-файл, затем POST; при сбое продолжать повторять попытку каждый цикл; переименовывать в `*.delivered` только после HTTP-успеха. Данные переживают отказы приёмника любой длительности. |

## Правила эксплуатации

1. **Приёмник — это инфраструктура, а не функция агента.** Дайте ему собственный unit и собственную политику перезапуска. Если он живёт внутри мира шлюза, инцидент шлюза становится и инцидентом приёма данных (наблюдалось: одна цепочка отказов уронила и то и другое, а утреннее измерение пролежало в очереди 12 ч).
2. **Один зависший клиент не должен иметь возможности убить сервер.** Однопоточные серверы на stdlib заклинивают на зависшем соединении — весь процесс перестаёт отвечать, включая его собственный ping-endpoint. Используйте `ThreadingHTTPServer` (или асинхронный сервер). Отказ «жив, но мёртв» бывает и у приёмных серверов, а не только у шлюзов.
3. **Логам и сертификатам не место в `/tmp`.** `/tmp` очищается при перезагрузке; приёмник, чей TLS-сертификат лежит там, умирает в наихудший возможный момент (утреннее измерение). Только постоянные пути.
4. **Никогда не терять измерение из-за сети.** Сторона устройства сначала пишет локально (`spool/*.json`), отправляет POST и помечает файл доставленным только при HTTP-успехе. При сбое повторяет попытку каждый цикл — бесконечно. Очередь — источник истины, а не сеть.
5. **Сканировать непрерывно, а не по расписанию.** BLE-наблюдатель, сканирующий «5:10–5:20», пропустит пользователя, который измеряет в 5:08. Постоянно работающий цикл сканирования (12 с сканирование, 5 с пауза ≈ 17 с цикл) ловит любой всплеск advertisement-пакетов длиннее цикла — 6/6 живых перехватов в production. Никогда не просите пользователя подстраиваться под окно.
6. **Health check = реальный запрос, а не проверка порта.** `ss -tln` показывает порты как «прослушиваемые» у заклинившего процесса. Watchdog должен выполнять HTTP-PING приёмника (`GET /ping`, ожидать 200 в течение нескольких секунд).
7. **Проверять end-to-end без устройства.** Отправьте POST с синтетическим измерением и реальным токеном через TLS-прокси и убедитесь, что строка попала в SQLite; затем удалите её. Доказывает цепочку приёмник → БД до того, как вы начнёте отлаживать BLE.
8. **Оповещать о переходах состояния.** Watchdog на стороне VM/устройства, проверяющий приёмник каждые 5 минут, должен оповещать один раз за инцидент (файл состояния) с напоминанием не чаще, чем раз в 30 минут, — а не при каждом опросе.

## Хронология отказа (наблюдавшаяся)

```
02:00  receiver dies (stuck client / killed with an unrelated restart chain)
05:08  user measures; device BLE daemon receives the reading (24/7 scan)
05:08  POST fails (connection refused) → reading spooled, retry every ~17 s
05:08–15:15  retries fail; nothing restarts the receiver (its cron lifeline is down too)
15:15  receiver unit starts (new architecture); first retry succeeds → delivered
15:15  spool flushed, *.delivered renamed; morning reading lands in SQLite intact
```

Полные потери: **ноль**. Задержка: 12 ч, целиком вызванная отсутствующей политикой перезапуска — исправление, которое этот модуль и поставляет.

## Тестирование без устройства

```bash
# simulate a device: POST one reading through the TLS proxy
curl -sk -X POST https://intake.example:8899/health/webhook \
  -H "X-Health-Token: $(cat /path/to/token_file)" \
  -H "Content-Type: application/json" \
  -d '{"source":"test","metrics":[{"metric":"heart_rate","value":60}]}'
# → {"status":"ok","stored":1}; then DELETE the row in SQLite.
```

## Окружение

Receiver читает свой токен из файла токена при запуске (никогда из конфигурации, в которой может остаться устаревший пример). Юниты задают `HOME` явно — `expanduser()` внутри пользовательских юнитов systemd этого требует.
