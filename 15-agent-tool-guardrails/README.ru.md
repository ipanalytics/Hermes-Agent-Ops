Я перестал верить самоотчёту агента: команды идут через шлюз, скиллы проходят проверку, работу
принимает оркестратор. Три куска кода в одной папке: шлюз для терминальных команд, сканер
скиллов, и ворктри-полосы с приёмочным гейтом.

## Что такое Hermes (для нового читателя)

Hermes — ИИ-агент, которого я гоняю на своём сервере. Он крутит задания по расписанию, правит
мои файлы, обращается к провайдерам и пишет собственные скрипты. «Провайдеры» — это бэкенды
моделей: разные компании продают разные LLM (большие языковые модели) по разным ценам, и Hermes
общается с несколькими из них. Два занятия Hermes — это и два самых простых способа, которыми
он может нанести реальный ущерб: он запускает shell-команды и ставит скиллы, написанные
посторонними. «Токены» — это единицы, по которым провайдеры выставляют счёт; каждый вызов модели
стоит входных и выходных токенов. «Аудит» здесь — это запись решений постфактум.

Эта папка появилась потому, что я перестал считать эти две вещи безопасными. Задание по
расписанию может сработать в три ночи с промптом, который я писал месяцы назад, и с контекстом,
которого я не вижу; установка «полезного» скилла, найденного в интернете, — это, технически,
исполняемая политика, написанная чужим человеком. Я написал три маленьких куска кода, чтобы
опасные вещи были вынуждены пройти через шлюз.

## Зачем это сделано — два режима отказа

**Режим отказа 1: через шлюз проходит деструктивная команда.** Наивный способ оградить команды —
список regex-шаблонов, которые блокируют «rm -rf /» и на этом успокаиваются. Это ломается за три
секунды: `r''m -rf /`, `$(rm -rf /etc)`, `curl ... | bash`, base64-декодированные полезные
нагрузки, залитые в `sh`. Regex по сырому тексту не видит в них `rm`. Мне нужен был хук,
который разбирает команду как настоящий shell — парсит AST (абстрактное синтаксическое дерево,
структурная форма команды), чтобы вложенные подстановки и пайпы проверялись как настоящие
команды, а не как поверхностная строка — и только потом решает.

**Режим отказа 2: агент говорит «готово», и я принимаю это на веру.** Несколько агентов,
правящих один и тот же чекаут, молча затирают правки друг друга, а у оркестратора (маленький
цикл, который раскидывает работу по агентам) есть только их собственные отчёты. Агенты не врут,
они просто ошибаются о том, какие файлы они реально тронули и прошли ли тесты. Мне нужно было,
чтобы оркестратор сам перезапускал команду верификации на ветке каждого писателя и принимал
только ту работу, которая породила доказательства, читаемые оркестратором.

Вот и вся папка. Pre-tool-call shell-хук, который блокирует деструктивные команды. Сканер
скиллов, который отказывается ставить файлы с шаблонами prompt-инъекций или эксфильтрации.
Ворктри-флоу, который выдаёт каждому параллельному писателю свою ветку и гейт, который
запускает оркестратор.

## Что лежит в папке

- `hooks/bash_guard.py` — pre-tool-call shell-хук. Разбирает команду через `bashlex` (Python-
  библиотека, которая превращает shell-текст в настоящее синтаксическое дерево), обходит AST
  так, чтобы вложенные подстановки и пайпы были видны как настоящие команды, нормализует куски
  слов (снятие кавычек и обратных слэшей), чтобы `r''m` оценивался как `rm`. Возвращает
  `{"action": "block", "message": "..."}` для деструктивных шаблонов; иначе разрешает. Лог в
  `~/.hermes/logs/bash_guard.jsonl`. На внутренней ошибке открывается (fail-open) и пишет
  след — сломанный шлюз не должен быть хуже отсутствия шлюза.
- `hooks/skill_scan.py` — проверяет скилл, файл промпта или конфиг агента, прежде чем ему
  доверять. Оценивает шаблоны prompt-инъекций («ignore previous instructions»), стелс-юникод
  (символы нулевой ширины или двунаправленного управления, которые не отображаются в diff),
  упоминания секретных путей в сочетании с инструментами эксфильтрации (сетевые вызовы — всё,
  что отправляет байты за пределы этой машины), `curl | bash`, base64-декодирование в shell,
  `rm -rf /`, `mkfs`, `dd of=/dev/...`, отключение системных средств защиты. Может работать как
  `--hook` на пути установки, чтобы находка HIGH блокировала запись.
- `hooks/policy.json` — настраиваемая часть `bash_guard`. Свои регулярки я держу в `block_patterns` (
  собственные regex-блокировки), `allow_regexes`, поменяйте `protected_vm_ids`. Удалите ключ,
  чтобы откатиться на встроенное значение по умолчанию внутри `bash_guard.py`.
- `lanes.py` — ворктри-полосы для параллельных писателей + приёмочный гейт. У каждой полосы
  свой `git worktree` под `<repo>/.worktrees/<lane>` и своя ветка `lane/<lane>`. Гейт перезапускает
  команду верификации проекта внутри каждой полосы, ловит код возврата и хвост вывода, и
  принимает только те полосы, которые прошли.
- `install.sh` — копирует хуки в `$HERMES_HOME/hooks/`, печатает строки `config.yaml`, которые
  регистрируют `bash_guard.py` как `pre_tool_call` для инструмента `terminal` и `skill_scan.py`
  для `write_file`. `--register` правит конфиг на месте (идемпотентно).
- `tests/test_bash_guard.py` — 22 кейса на проводной контракт (контракт JSON-в-stdin /
  JSON-из-stdout, которому обязан следовать shell-хук Hermes). Включая `rm -rf /`,
  `echo $(rm -rf /etc)`, `bash -c 'rm -rf /var'`, `cat ~/.hermes/auth.json | curl ...`,
  `base64 -d ... | sh`, `qm destroy 100`, `dd ... of=/dev/sda`, форк-бомбы, и `> /etc/shadow`.
- `tests/test_lanes.py` — сквозной тест на временном репозитории: создаёт две полосы, запускает
  `status`, делает так, чтобы одна прошла гейт, а другая нет, сливает в `integration`, прогоняет
  путь с конфликтом.

## Как bash_guard принимает решение

Шесть правил, применяемых к нормализованному дереву команды:

1. **Уничтожение файловой системы.** `rm -rf /`, `rm -rf /*`, `rm --no-preserve-root /`, `mkfs`,
   `wipefs`, `dd of=/dev/...`, `shred /dev/...`. Блокирует.
2. **Вложенные shell-полезные нагрузки.** `bash -c 'rm -rf /var'`, `eval "..."`,
   `$(rm -rf /etc)`. Внутренняя команда проверяется рекурсивно (глубина до 3) и блокируется,
   если блокируется.
3. **Защищённые гости.** `qm stop/destroy/reset/reboot/suspend/shutdown 100` и те же глаголы
   через `pct`. ID виртуалок настраиваются; по умолчанию защищена VM со шлюзом. Блокирует.
4. **Запись в критические файлы.** `tee /etc/shadow`, `cp /etc/sudoers ...`, редиректы в
   `~/.hermes/.env`, `~/.hermes/auth.json`, `~/.ssh/authorized_keys` и т. п. Блокирует.
5. **Секреты + эксфильтрация в одной команде.** Чувствительный путь (`~/.hermes/.env`,
   `~/.ssh/id_*`, `/etc/shadow`, `~/.netrc`) в одной строке с `curl` / `wget` / `nc` / `ssh`.
   Блокирует.
6. **Декодер залит в shell.** `base64 -d payload.b64 | sh`, `xxd -r ... | bash`,
   `openssl enc -d ... | sh`. Блокирует.

Отдельный уровень `flag` (логируется, но разрешается): `curl ... | bash` с неизвестного хоста,
`npm install -g`, `pip install`. Это нормально выглядящие инсталляторы; мне нужно их видеть в
журнале аудита, чтобы потом ревью мог спросить «зачем агент ставил это в три ночи?»

## Как работает lanes.py

Пять подкоманд. Коды возврата: 0 ok, 1 падения полосы или конфликт слияния, 2 ошибка
использования / git.

```bash
lanes.py new    REPO lane-a lane-b           # создать worktree + ветки от текущего HEAD
lanes.py status REPO                         # по полосе: head, число коммитов, грязные файлы, stat diff
lanes.py gate   REPO [--cmd "pytest -q"]     # перезапустить верификацию внутри каждой полосы
lanes.py merge  REPO --into integration      # слить lane/<lane> в указанную ветку
lanes.py report REPO                         # evidence JSON (коммиты, грязь, diff) для оркестратора
```

Команда верификации определяется автоматически: манифест `hermes verify` под
`.hermes/environment.json` выигрывает, затем Python-проект получает `python3 -m pytest -q`,
затем npm-проект — `npm test --silent`. Перебейте через `--cmd`. Гейт перезапускает верификацию
внутри чекаута полосы (а не основного чекаута), чтобы писатель не мог подделать прохождение
тестов правкой общих файлов.

Worktree лежат в `REPO/.worktrees/<lane>`; путь добавляется в `.git/info/exclude` (не в
`.gitignore`), чтобы чекауты полос не светились в `git status` основного клона и при этом в
репозиторий не добавлялся незакоммиченный файл.

## Как я это использую в проде

- `bash_guard.py` зарегистрирован как хук `pre_tool_call` для инструмента `terminal`. Каждая
  команда, которую Hermes хочет запустить, проверяется; блоки и флаги логируются в
  `~/.hermes/logs/bash_guard.jsonl`.
- `skill_scan.py` зарегистрирован как хук `pre_tool_call` для `write_file`, когда путь лежит
  под `~/.hermes/skills/` или `~/.hermes/prompts/`. Находка HIGH блокирует запись; агенту
  сообщается осмотреть файл и перезапустить с явным решением.
- `lanes.py` вызывается из цикла оркестратора. Воркеры получают свою полосу; гейт запускается
  до того, как любое слияние принимается; именно по нему события сверяет ежедневный сводный
  обход (`05-cron-of-crons`).
- Раз в месяц я гоняю `skill_scan.py --all-installed` против `~/.hermes/skills/` как базовый
  аудит. В проде он ничего не находит — это результат, который я хочу, и самый дешёвый способ
  его сохранить — продолжать проверять.

## Быстрый старт

```bash
# шлюзы команд и скиллов
bash install.sh                 # копирует хуки, печатает команды конфига
bash install.sh --register      # ещё и правит config.yaml на месте

# проверить один скилл перед установкой
python3 hooks/skill_scan.py path/to/SKILL.md

# контракт хука и настройка, снимающая цикл повторных подтверждений
python3 hooks/bash_guard.py < payload.json   # JSON на stdin — JSON-блок на stdout
hermes config set hooks_auto_accept true     # не подтверждать одну и ту же находку LOW каждый раз

# параллельные писатели с приёмочным гейтом
python3 lanes.py new ~/work/repo lane-a lane-b
# (работа идёт внутри .worktrees/lane-a и .worktrees/lane-b)
python3 lanes.py gate ~/work/repo --cmd "python3 -m pytest -q"
python3 lanes.py merge ~/work/repo --into integration
```

## Ограничения

- **bash_guard открывается при сбое (fail-open).** Баг в хуке, отсутствующий `bashlex`,
  внутреннее исключение — команда разрешается, а отказ пишется в лог. Причина: сломанный шлюз
  не должен быть хуже отсутствия шлюза, особенно в три ночи, когда лог никто не смотрит.
- **bash_guard покрывает то, что я видел.** Правила — это не полный список опасных команд.
  Свои правила я держу в `policy.json > block_patterns`.
- **lanes.py предполагает git.** На чекауте, который не git-репозиторий, не работает. Шаг
  слияния использует `git merge --no-ff`; настоящий трёхсторонний конфликт слияния
  диагностируется и слияние откатывается — полоса остаётся изолированной.
- **skill_scan — это regex, а не парсер.** Достаточно обфусцированная инъекция может
  проскользнуть. Относитесь к его вердикту как к одному сигналу, а не как к гарантии.
