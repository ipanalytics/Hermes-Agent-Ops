# 16 — gepa-skill-tuner

**Оптимизируйте параметр, который вы реально поставляете, — промпт или SKILL.md — на наборе задач с эталонными ответами.**

> GEPA (*Reflective Prompt Evolution Can Outperform Reinforcement Learning*, arXiv 2507.19457,
> ICLR 2026 Oral, MIT) улучшает текстовые параметры, позволяя LLM **читать полные трассировки
> выполнения** и рефлексировать на естественном языке вместо сворачивания rollout в одно
> скалярное вознаграждение. Заявленные результаты: до 35× меньше rollouts, чем у GRPO,
> +6…20% поверх него и рост с 55% до 82% у кодинг-агента за счёт автоматически выученных
> навыков. Для агента, чьи поставляемые знания *являются* текстом (system prompt, cron prompt,
> skill), это напрямую ложится на артефакт.

## Что здесь есть

- `tuner.py` — одна команда: стартовый промпт (или одна секция SKILL.md) + набор задач в
  JSONL + метрика → JSON-отчёт с валидационной оценкой каждого кандидата и unified diff.
- `tests/test_dedupe.py` — шаг дедупликации, покрытый тестами (схлопывание, конфликты
  меток, стабильность порядка); запускается обычным `python3` или `pytest`.
- `examples/shell-safety/` — размеченный набор задач из 30 строк из модуля 15, готовый к запуску.

## Как использовать

```bash
python3 -m venv --without-pip .venv && curl -sSL https://bootstrap.pypa.io/get-pip.py | .venv/bin/python
.venv/bin/pip install -r requirements.txt

# plain prompt file
.venv/bin/python tuner.py --prompt-file seed_prompt.txt --dataset tasks.jsonl --out report.json

# one section of a skill, custom metric, then write the winner back
.venv/bin/python tuner.py --skill ~/.hermes/skills/foo/SKILL.md --section "## Rules" \
    --dataset tasks.jsonl --evaluator my_metric.py --max-metric-calls 150 --write
```

Метрика — это либо точное/подстрочное совпадение по полю `answer`, либо ваш собственный
модуль `evaluate(data, response) -> (score, feedback)`. API-ключ задаётся так же, как у
агента (`OPENROUTER_API_KEY` в окружении или `~/.hermes/.env`).

## Дубликаты — первая ошибка в наборе задач, а не деталь

`tuner.py` схлопывает повторяющиеся входы перед разбиением train/val (схлопывание
пробельных символов, приведение регистра). Пропуск этого шага наносит три отдельных вида ущерба:

- **Утечка данных.** Разбиение — это срез файла, поэтому повторяющийся запрос и участвует
  в оптимизации, *и* оценивается. Валидационная цифра растёт, а промпт не улучшается.
- **Запоминание.** Рефлексивный оптимизатор читает трассировки и переписывает инструкции
  прозой; показав ему одну и ту же строку пять раз, вы получите объяснение *именно этой
  строки*, а не правила за ней. Повторяющиеся данные сильнее всего бьют по
  mixture-of-experts моделям (см. *MoE models overfit more to repeated data*,
  arXiv 2609.11917) — а именно к ним относится большинство облачных моделей для задач.
- **Стоимость.** Каждая копия — ещё один оплачиваемый rollout из бюджета, который вы
  объявили заранее.

Измерено на реальном наборе для маршрутизации (логи запросов агента → имя навыка, тот
случай, под который этот модуль и создавался):

| | строк | после разбиения | пересечение входов train ∩ val | конфликтующие метки |
|---|---|---|---|---|
| исходный | 124 | 86 / 38 | 1 | 30 групп |
| `tuner.py` (дедупликация включена) | 70 | 49 / 21 | 0 | сообщается по каждой группе |

Запуск также печатает, что было отброшено и какие конфликты разрешены
(`kept 'home-infra-ops' out of {'home-infra-ops': 1, 'personal-health-pipeline': 1}`) и
сохраняет всё это в отчёте в поле `dataset`. Метка большинства побеждает в группе; при
равенстве сохраняется первое вхождение. Конфликты выносятся наружу и никогда не
усредняются молча — набор, где один и тот же запрос имеет четыре разных «правильных»
ответа, — это проблема разметки выше по потоку, и никакой промпт её не исправит.
`--keep-duplicates` запускает старое поведение, если хотите показать разницу.

## Правила

1. **Набор данных очищается до любых измерений.** Дублирующиеся входы схлопываются, конфликты
   меток докладываются (см. раздел выше); без этого разбиение даёт утечку, а оптимизатор
   учит повтор вместо правила.
2. **Стоимость объявляется до старта.** `--max-metric-calls` — весь бюджет; прогон из
   60 вызовов на дешёвой модели — это секунды и центы.
3. **Отложенное разбиение — всегда.** Докладываемая оценка — валидационная, а не
   обучающий мини-батч.
4. **Никаких фальшивых улучшений.** Если ничто не превзошло стартовый промпт, инструмент так
   и говорит (`No prompt change survived validation`) и не записывает дифф. Наш пример
   shell-safety делает именно это с сильной моделью для задачи — стартовый промпт уже на
   потолке, собирать нечего. Выберите задачу, где узкое место — именно *промпт*.
5. **Ревью как изменения кода.** Выход — дифф плюс оценка по каждому кандидату; регрессия в
   диффе видна, а файл затрагивается только с `--write`.

## Рецепт: промпт для маршрутизации из логированного трафика

Дешёвый повторяемый цикл, ради которого написан этот модуль:

1. **Сбор.** Извлечение пар (запрос → фактически использованный навык/инструмент) из хранилища сессий агента — реальные запросы, включая неаккуратные надиктованные, а не написанные вручную примеры.
2. **Разметка.** Оставляйте только строки, результат которых поддаётся проверке (навык действительно запускался, задача выполнена успешно). Отбрасывайте неоднозначные вместо того, чтобы угадывать: 30 из 70 уникальных строк в нашем наборе были размечены более чем одним способом, и такие строки ничему не учат тюнер.
3. **Дедупликация** (автоматическая, см. выше) и проверка выведенного отчёта о конфликтах, прежде чем потратить хотя бы один rollout.
4. **Настраивайте с небольшим бюджетом.** `--max-metric-calls 20` на 70 уникальных строк — это одна итерация за 8 секунд; увеличивайте значение, только когда кандидат улучшает оценку на отложенной выборке (holdout).
5. **Поставляйте diff, а не отчёт.** Победивший промпт возвращается в маршрутизатор как изменение, прошедшее ревью (`--write` или патч), и после этого на той же holdout-выборке выполняется повторный прогон, чтобы подтвердить, что выигрыш сохранился на данных, которые оптимизатор никогда не видел.

## Место в развёртывании агента

Запускайте его на поверхностях с реальным, воспроизводимым уровнем отказов и дешёвой разметкой:

- **cron-промпт**, который продолжает выдавать элементы, отклоняемые оператором,
- **раздел навыка**, чей чек-лист умеет оценивать `hermes verify`,
- **промпт маршрутизации/диспетчеризации**, оцениваемый по залогированным парам (запрос → корректный инструмент/навык).

Не направляйте его на задачу, которую модель уже решает; запуск сообщит об отсутствии изменений.

## Примечания по безопасности

- Устанавливайте в изолированный virtualenv внутри `$HERMES_HOME/venvs/`. `litellm` 1.82.7/1.82.8 были помечены на PyPI как вредоносные; файл зависимостей закрепляет версии в обход них, а собственный сканер пакетов Hermes предупреждает перед установкой.
- Настроенный промпт остаётся промптом: прогоняйте любого кандидата, который будет исполнять команды, через `bash_guard` модуля 15, прежде чем доверять ему.
