# 17 — model-slot-bakeoff

_English version: [README.md](README.md)_

Прайс-лист — это доллары за миллион токенов. Он не говорит, сколько мне стоит один запрос. Этот модуль прогоняет одни и те же настоящие задачи через несколько моделей и показывает, какая отвечает верно, какая быстро и сколько с меня сняли за каждый ответ.

> Модель с рассуждениями может сжечь в шесть раз больше выходных токенов, чем обычная, на том же самом промпте, поэтому модель, более дешёвая за токен, в итоге оказывается более дорогой за задачу — и более медленной. Единственный способ узнать это — прогнать реальную работу слота через обе и посмотреть на счёт, на часы и на то, был ли ответ действительно верным.

## Hermes в одном абзаце

Hermes — ИИ-агент, который живёт на моём сервере. Каждая именованная роль в его нагрузке — исследование, код, суммаризация, дайджест — это *слот*: одна запись в конфиге, которая говорит «для задач такого типа по умолчанию используй модель X». Слот можно поменять (приехала новая модель, изменилась цена, старую сняли с продажи), и тогда мне нужно знать, безопасна ли замена: достаточно ли новая модель корректна, достаточно ли быстра, дешевле ли она, поддерживает ли вызовы инструментов, если слоту они нужны. Эта папка — стенд, который отвечает на эти четыре вопроса цифрами, а не догадками.

## Что у меня есть

- `bakeoff.py` — прогоняет один набор задач через N моделей-кандидатов, оценивает каждый ответ по скрытому тесту и пишет JSON-отчёт и сводную таблицу.
- `examples/slot-check/` — набор из двух задач со скрытыми тестами и три кандидата на слот для кода (обычная модель-кодер, модель с рассуждениями и та же модель с пониженным усилием рассуждений).
- `tests/test_bakeoff.py` — офлайн-тесты на оценивание, загрузку и пути ошибок.

## Словарь, который я здесь использую

*Токен* — это примерно слово или кусочек слова, единица, по которой API выставляет счёт. *Модель с рассуждениями* (reasoning model) перед ответом думает вслух — и я плачу за каждое слово этого размышления. Поэтому модель, которая выглядит дешёвой в каталоге, тихо может обходиться в шесть раз дороже за задачу, чем её скромный сосед по списку.

*Шлюз* (gateway) — посредник, куда я шлю запросы (у меня это OpenRouter, но сгодится любой с OpenAI-совместимым API). *Апстрим* (upstream) — компания, чья модель реально ответила. Шлюз выбирает апстрим сам, и не всегда тот, кого я имел в виду. Ключ API я читаю из `OPENROUTER_API_KEY` — либо из переменной окружения, либо из `~/.hermes/.env`.

*Скрытый тест* — маленькая проверка, которую я пишу сам; модель получает задачу, но не тест, так что «passed» значит: ответ правда работает. Стенд запускает блок кода модели на тесте во временной директории через `subprocess.run` с таймаутом, поэтому неправильное решение печатает однострочный хвост ошибки, а правильное — `OK`. Собственное заявление модели об успехе в зачёт не идёт.

*Вызов инструмента* (tool call) — когда модель просит запустить один из инструментов агента; без этого модель агентом быть не может. *Задержка* (latency) — время одного ответа, замеренное у меня между отправкой запроса и чтением ответа. *Стоимость* (cost) — то, что шлюз сообщил за вызов (`usage.cost` в ответе): токены рассуждений уже внутри счёта, отдельной арифметики не нужно.

## Что я меряю у каждого кандидата

| Сигнал | Почему он в отчёте |
|---|---|
| `passed` | решает скрытый тест, а не заявление самой модели — кандидат теста никогда не видит |
| `avg_cost_per_task_usd` | то, что шлюз выставил за этот вызов, включая токены рассуждений |
| `completion_tokens` | показывает, *почему* модель, дешёвая за токен, дорога за задачу |
| `served_by` | маршрутизация даёт не всегда то, что я просил; это апстрим, который реально ответил |
| `avg_latency_s` | слот на критическом пути пользователя платит за медленного кандидата на каждом запросе |
| `tool_call_ok` | с `--with-tools`: модель, которая ни разу не вызывает инструмент, не удержит агентский слот |

Первые три столбца — прохождение, цена, токены — вместе отвечают на «безопасна ли замена и сколько она стоит?». Четвёртый, `served_by`, ловит случаи, когда каталог врёт. Пятый — то, что я проверяю, прежде чем поставить кандидата на горячий путь. Шестой — то, что вообще делает агентский слот агентским.

## Как я этим пользуюсь

```bash
python3 bakeoff.py --candidates candidates.json --tasks tasks.json --with-tools
```

API-ключ читается из `OPENROUTER_API_KEY` (переменная окружения или `~/.hermes/.env`). `BAKEOFF_API_URL` я направляю на любой OpenAI-совместимый эндпоинт, чтобы мерить другой шлюз — скрипт работает через urllib по стандартному пути `chat/completions`, так что подходит любая drop-in замена. URL по умолчанию — `https://openrouter.ai/api/v1/chat/completions`. `--out` указывает, куда ляжет JSON-отчёт (по умолчанию `bakeoff-report.json`). `--max-tokens` ограничивает длину ответа модели; по умолчанию 2000. Код возврата: 0 при завершённом прогоне, 2 при ошибке подготовки (нет ключа, плохой вход).

Список кандидатов — тестируемая модель, опциональная привязка к апстриму и опциональные поля запроса; именно здесь вариант с `reasoning_effort` становится отдельным кандидатом:

```json
[
  {"label": "incumbent", "model": "vendor/model-a"},
  {"label": "challenger", "model": "vendor/model-b", "provider": "FirstPartyCloud"},
  {"label": "challenger (low effort)", "model": "vendor/model-b", "extra": {"reasoning_effort": "low"}}
]
```

`label` — то, что видно в таблице; если поля нет, берётся id модели. Кандидат без `model` режется сразу, до отправки каких-либо запросов. Поле `provider` становится жёсткой привязкой (`{"only": [provider]}` в теле запроса) — шлюз не сможет упасть на другого поставщика. Поле `extra` мержится в тело запроса как есть — так в него попадают `reasoning_effort`, оверрайды сэмплинга и прочее.

Набор задач — промпт плюс тест, который оценивает ответ. Оценка запускает блок кода модели на тесте во временной директории, поэтому задачи должны быть проверяемыми:

```json
[
  {"name": "flaky-input",
   "prompt": "Write a Python function `pick(items, key, k)` ... Answer with one ```python block only.",
   "test": "from solution import pick\nassert pick([{'n': 1}], 'n', 1) == [{'n': 1}]\nprint('OK')"}
]
```

Стенд вытаскивает из ответа модели первый блок кода в тройных backticks и прогоняет на нём тест. Если блока нет, в ход идёт весь ответ — это удобно для лаконичных кандидатов, которые печатают только функцию. Тест с импортом `solution` — каноническая форма; стенд пишет код модели в `solution.py`, а тест — в `test_solution.py` внутри `tempfile.TemporaryDirectory`. Поддерживается и JSONL наряду с обычным JSON-массивом — это то, что я использую, когда набор задач переваливает за пару штук.

## Измеренный пример

`examples/slot-check`, две оцениваемые задачи, один прогон (все три кандидата обслужены одним и тем же first-party-апстримом, все трое прошли оба скрытых теста):

| кандидат | прохождение | средняя задержка | средняя стоимость / задача | выходные токены / задача |
|---|---|---|---|---|
| обычная модель-кодер | 2/2 | 3.0 с | $0.00077 | 435 |
| модель с рассуждениями, усилие по умолчанию | 2/2 | 134.0 с | $0.01655 | 12 938 |
| модель с рассуждениями, низкое усилие | 2/2 | 13.8 с | $0.00234 | 1 796 |

Я намерил одинаковый результат у всех троих, разницу в 21× в цене одного запроса и 45× в задержке — и вся эта разница ушла на токены рассуждений, которых модель без размышлений вообще не производит. Снижение усилия у модели с рассуждениями возвращает её к тройной обычной цене при четверти токенов. Эта таблица и есть вся суть: по прайс-листу я бы выбрал модель с рассуждениями и платил бы в 21 раз больше за те же ответы. Тот же набор задач в другой день или с другой смесью задач сдвинет эти числа — поэтому я гоняю стенд, а не верю таблице цен.

Третью строку я обычно и оставляю. Модель с рассуждениями на полном усилии верна, но дорогая и медленная; та же модель на низком усилии верна, не сильно дороже, и всего на четыре секунды медленнее обычной. Это и есть замена.

## Три отказа, которые это ловит, а прайс-лист прячет

1. **Токены рассуждений.** Выходные токены — дорогая половина счёта, и за размышления модели тарифицируются отдельно. Сравнивать цену за токен между думающей и недумающей моделью — значит сравнивать не ту цифру; нужна цена за задачу на одном и том же наборе.
2. **Маршрутизация.** `served_by` сообщает апстрим, который реально ответил. Модель, чьи единственные апстримы лежат вне списка разрешённых провайдеров аккаунта шлюза, падает с `HTTP 404: No allowed providers are available for the selected model`, хотя каталог её содержит и статус эндпоинта исправен — тело ошибки называет и апстримы модели, и список разрешений, и это единственное место, где сказано, почему модель нельзя вызвать. Я прописываю привязку через `"provider": "<name>"`, когда знаю, какой апстрим мне нужен. Стенд сохраняет тело ошибки в строке `error` внутри задачи, чтобы причина маршрутизации дожила до JSON-отчёта.
3. **Вызовы инструментов.** Для агентского слота поддержка вызовов инструментов — жёсткое требование, а не бонус. `--with-tools` проверяет её одним запросом: фиксированный промпт («List the files in /tmp with the shell tool.») с описанием одной функции в теле. Модель, которая выдала ожидаемый вызов функции, получает `tool_call_ok: yes`; модель, которая отвечает прозой — `tool_call_ok: no`; модель, которая вернула ошибку — текст ошибки и `no`.

## JSON-отчёт

`--out` пишет в stdout краткую таблицу, а на диск — структурированный отчёт:

```json
{
  "candidates": [
    {
      "label": "incumbent", "model": "vendor/model-a",
      "provider_pin": null, "extra": null,
      "tasks": [
        {"name": "task-1", "served_by": "...", "latency_s": 3.0,
         "prompt_tokens": 412, "completion_tokens": 130,
         "reasoning_tokens": 0, "cost_usd": 0.00012,
         "verdict": "pass"}
      ],
      "totals": {"tasks": 2, "passed": 2, "cost_usd": 0.00154,
                 "avg_cost_per_task_usd": 0.00077,
                 "avg_latency_s": 3.0, "completion_tokens": 435},
      "tools": {"tool_call_ok": true, "tool_call_s": 2.4}
    }
  ],
  "tasks": 2
}
```

Этот файл я коммичу рядом с конфигом слота: замороженный снимок того, сколько стоили кандидаты в тот момент. Через полгода, когда цена слота тихо поползёт вверх или кто-то предложит замену, старый отчёт — то, с чем я сравниваю новый прогон.

## Как часто я это гоняю

- Каждый раз, когда каталог меняет цену текущей модели слота.
- Каждый раз, когда я подумываю заменить текущего кандидата на того, кто на бумаге дешевле.
- После любой переписки промпта, способной сдвинуть форму задачи слота — другой промпт обычно двигает счётчик токенов, а тот двигает счёт.
- Раз в квартал на том же наборе задач — чтобы поймать тихую деградацию текущей модели до того, как она всплывёт в продакшене.

## Границы

- Несколько задач — это проверка на живучесть, а не бенчмарк. Он отвечает на вопрос «какой кандидат дешевле и при этом верен для *этого* слота», а не «какая модель умнее».
- Стоимость — то, что шлюз сообщил по каждому вызову; попадания в кэш и скидки на стороне провайдера не моделируются.
- Задержка плавает вместе с нагрузкой на апстрим: кандидатов я сравниваю внутри одного запуска, а не по разным дням.
- Стенд исполняет написанный моделью код, чтобы его оценить. Скрытые тесты я держу без внешних зависимостей, а запускаю в одноразовом окружении, когда тестируемые модели не заслуживают доверия.
