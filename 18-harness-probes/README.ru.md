**Приёмочный гейт для обвязки агента: детерминированные пробы, явная база «как должно быть» и флаг регрессии на каждое изменение.**

Hermes — мой домашний ИИ-агент: живёт на моём сервере, работает по расписанию и сам ведёт рутину — дайджесты, слежение за ценами, мониторинг здоровья, надзор за собственными сбоями. Всё, что окружает саму модель, я называю *обвязкой* (harness): файлы промптов, расписания в `cron` (системный планировщик, который запускает команды в назначенное время), сторожевые скрипты для лимитов бюджета, таблицы маршрутизации, обёртки доставки дайджестов. Обвязка меняется каждый день. Правка может тихо сломать то, что работало вчера, — а сбой не похож на падение. Агент продолжает отвечать в чате, кроны продолжают срабатывать, а регрессия всплывает через три дня как пропавший раздел дайджеста или повторная закачка. Этот режим отказа и есть причина, по которой существует эта папка.

## Зачем это нужно

До того как у меня появился этот гейт, одна «небольшая правка» сторожевого скрипта стоила мне тихой недели. Скрипт продолжал выходить с кодом 0; мой регистратор с удовольствием писал в лог пустоту; ниже по цепочке из дайджеста пропал целый блок. Я заметил это, когда человек в моём доме это заметил. Урок, который мне пришлось усвоить дважды: у обвязки нет собственного набора тестов. Промпты правятся, расписания сдвигаются, сторожевые скрипты переписываются, таблицы маршрутизации меняют провайдера. В каждом из этих мест может приземлиться регрессия, и ни в одном из них баг не объявляет о себе сам.

`probes.py` — моя попытка дать обвязке маленький честный приёмочный тест. Каждая проба — детерминированная проверка артефактов, которые агент обязан производить: свежие отчёты, непустые очереди, разбираемые файлы состояния, сторожевые скрипты, которые молчат, пока всё в пределах лимита, дайджесты с минимальным числом пунктов, свежие выводы заданий без учётных данных. Первый прогон, который прошёл, я замораживаю как базу. С этого момента любая правка обвязки — это две команды: `run` до правки, `check` после. `check` падает только на *регрессии* — пробе, которая в базе проходила, а теперь упала. Падения, которые и так уже падали, печатаются, но не блокируют: известный больной угол не парализует гейт.

## Что здесь значит «проба»

Проба — это одно обещание, видимое пользователю, записанное как запись в JSON. Чтобы добавить пробу, кода писать не нужно — виды, которые понимает раннер, покрывают почти всё, что мне нужно проверять, а файл проб — просто данные. Полный набор лежит в `examples/probe_set.example.json`; я копирую его в свой каталог данных, перенаправляю пути на свои артефакты, правлю значения и выполняю `accept`, чтобы записать его как базу.

Виды проб, которые идут в поставке:

| Вид | Что проверяет |
|---|---|
| `file_fresh` | файл есть, моложе N часов, не меньше M байт |
| `files_no_empty` | в каталоге очереди нет файлов нулевого размера |
| `json_keys` | JSON разбирается, обязательные вложенные ключи на месте, элементов не меньше N |
| `script_silent` / `script` | команда завершилась с кодом 0 и пустым / непустым / любым выводом |
| `text_match` | в файле есть регулярное выражение хотя бы N раз (например, три карточки в дайджесте) |
| `cron_output` | самый свежий файл вывода крон-задания существует, не старше порога, не короче порога и совпадает с обязательными/запрещёнными шаблонами |
| `secrets_clean` | в последних N файлах каталога нет строк, похожих на учётные данные |

Проба не смотрит на выход модели и не оценивает качество ответа. Она проверяет артефакты: файл отчёта записан, в спуле нет пустышек, JSON состояния разбирается и содержит нужные ключи, сторож бюджета не сработал, в дайджесте есть хотя бы три карточки, в последних 25 выводах каталога cron нет токена `sk-…`. Это та поверхность, на которой регрессии обвязки и проявляются.

## Как это работает

Раннер — один Python-скрипт, который принимает аргумент с режимом:

| Режим | Что происходит |
|---|---|
| `run` | выполняет все пробы, пишет `data/probes_last.json`, печатает падения, код 1 при любом |
| `check` | то же плюс сравнение с `data/probes_baseline.json`; регрессии дают код 1 |
| `accept` | записывает текущий результат как базу — осознанное действие, а не побочный эффект |
| `list` | печатает набор проб: идентификатор, вид, описание |

Повседневная схема:

```bash
python3 probes.py run      # до правки
python3 probes.py check    # после правки — код 1 при регрессии
```

`run` — это снимок: показывает текущее «проходит / не проходит» по каждой пробе и выходит с кодом 1 при любом падении. `check` — то, что мне действительно нужно перед внесением правки в обвязку: сравнивает с замороженной базой и выходит с кодом 1 только на регрессии. Проба, которая не проходит уже неделю потому, что я до неё не добрался, продолжит печатать своё падение, но не остановит чистую правку где-то ещё.

`accept` — единственное, что трогает `probes_baseline.json`. Я отношусь к нему так же, как к force-push — это осознанный, задокументированный акт, а не то, что случается побочным эффектом успешного прогона. Это свойство критично: набор проб, который дрейфует незаметно, хуже, чем полное отсутствие проб.

Все пути считаются от `HARNESS_HOME` (по умолчанию `~/.hermes`), поэтому один и тот же набор работает и на ноутбуке, и на сервере, и в контейнере. Обёртка `probes_check.sh` — это одна строка на bash, которая вызывает `probes.py check`; я использую её из cron, чтобы команда оставалась стабильной даже если я позже переименую или оберну что-нибудь.

## Быстрый старт

```bash
git clone <этот репозиторий> && cd 18-harness-probes
export HARNESS_HOME=$HOME/.hermes
cp examples/probe_set.example.json "$HARNESS_HOME/data/probe_set.json"
$EDITOR "$HARNESS_HOME/data/probe_set.json"       # укажите свои пути к артефактам
python3 probes.py run
python3 probes.py accept                           # зафиксировать хорошее состояние
```

В планировщик — как сторож, раз в час обычно достаточно:

```cron
55 * * * * /path/to/probes_check.sh   # молчит, когда всё в порядке; при регрессии печатает её
```

Код возврата — это то, что читает супервизор. `0` — норма, `1` — хотя бы одна проба упала (или, в режиме `check`, хотя бы одна регрессия), `2` — набор проб отсутствует. В здоровые часы stdout пуст и доставки нет — обёртка молчит, когда нечего сказать, и печатает регрессию только когда что-то изменилось.

## Почему база — отдельный файл

Это самое важное конструктивное решение. Набор проб, который дрейфует незаметно, хуже, чем отсутствие проб. Принятый результат лежит в `probes_baseline.json` и пишется только явным `accept`, поэтому определение «работает» меняется осознанно. Если я правил пробу и забыл повторно сделать `accept`, мой следующий `check` справедливо назовёт это регрессией; если я правил обвязку, а пробы всё ещё проходят, правка принимается по умолчанию. Приём взят из исследований о правке навыков и обвязки с учётом регрессий (arXiv 2605.29668: изменение допускается, только если отложенный набор проб не показывает ухудшения), и практика это подтверждает: ценность не в наличии тестов, а в отказе принимать правку, которая меняет одну зелёную галочку на другую.

Две команды — `run` и `check` — тоже отвечают на разные вопросы. `run` отвечает на «мой агент сейчас работает?»; `check` отвечает на «моя последняя правка что-то сломала из того, что работало?». `run` я запускаю, когда что-то ощущается не так; `check` — после каждой правки обвязки. Обе пишут в `data/probes_last.json`; только `accept` пишет в `probes_baseline.json`.

## Выходные данные

Раннер пишет JSON-отчёт на каждом запуске, чтобы потом можно было строить графики или скормить его другому инструменту. `data/probes_last.json` выглядит так:

```json
{
  "checked_at": "2026-09-13T16:55:02",
  "total": 7,
  "passed": 7,
  "probes": [{"id": "report-fresh", "kind": "file_fresh", "ok": true, "why": "2166 б, 2.1 ч назад"}]
}
```

Каждая запись о пробе несёт свой идентификатор, вид, признак «прошла / не прошла» и однострочное человекочитаемое `why` — например, `"старый: 51.4 ч > 30 ч"` или `"совпадений 2 < 3"`. Коды возврата: `0` — норма, `1` — падение (или регрессия в режиме `check`), `2` — нет набора проб. Обёртка возвращает те же коды, поэтому подойдёт любой супервизор, понимающий ненулевой код.

## Эксплуатационные замечания

Это правила, которые я усвоил на собственном опыте. Их нет в `probes.py`; именно они заставляют `probes.py` оставаться честным.

- Пробы должны быть детерминированными. Проба, в выводе которой есть метка времени, будет выглядеть изменившейся каждый прогон; метки времени — в отчёт, не в проверки. Я усвоил это, когда проба «дайджест свежий» упорно регрессировала каждое утро — причина была в часах, вшитых в содержимое файла, а не в mtime файла.
- `secrets_clean` печатает имя файла, но не найденное значение, чтобы лог прогона сам не стал каналом утечки. Если скрипт когда-нибудь напечатает `sk-XXXXXXXX…` вместо имени файла — это баг, который нужно исправлять немедленно.
- Одна проба — одно обещание, видимое пользователю. Если проба падает по причине, которую я принимаю навсегда, это решение: правьте пробу, затем `accept`. Я не позволяю пробе лгать месяцами; лгущие пробы разъедают доверие к тем, что ещё кусаются.
- Набор должен прогоняться меньше чем за минуту. Медленные пробы в спешке начинают пропускать, а момент, когда я готов пропустить пробу, — это и есть момент, когда она бы что-то поймала.
- Набор проб — это данные, а не код. Правка `probes.py` — гораздо более серьёзное решение, чем правка JSON; я отношусь к скрипту как к инфраструктуре, а к JSON — как к конфигурации.
- Когда я добавляю новую пробу, я сначала пишу её так, чтобы она падала, запускаю её, смотрю, как она падает по ожидаемой причине, а потом либо правлю артефакт, либо правлю пробу. Проба, которая проходит с первого раза, подозрительна — обычно она проверяла не то.

## Границы применимости

В границах: детерминированная проверка собственных артефактов агента и сторожевых скриптов.
Вне границ: оценка качества ответов модели (для измерения того, что пропускает автоматика, — модуль 21), нагрузочное тестирование, юнит-тесты прикладного кода. Пробы — это про *то, что обвязка пообещала миру*, а не про то, что модель сделала с промптом.

## Сценарии

Я использую эту папку для четырёх вещей и пользовался для других, которые не предвидел:

- Агенты по расписанию, где никто не смотрит каждый прогон. Пробы делают обзор сами.
- Сторожевые скрипты (лимиты бюджета, контроль доставки), которые обязаны молчать в норме. Проба, которая запускает страж и проверяет молчание, ловит случай, когда рефакторинг случайно сделал стража шумным.
- Конфигурации на нескольких машинах, где одна и та же обвязка живёт на VPS и дома. Переменная `HARNESS_HOME` означает, что один файл проб покрывает обе машины.
- Любой конвейер, у которого отказ выглядит как «файл не появился», а не «процесс упал». Для случая «неправильно» проба не поможет; нужна оценка, а не проверка.

## Ограничения

Хочу быть прямым о том, чего эта папка не делает.

- Пробы проверяют то, что кто-то записал. Обещание, которое никто не занёс в набор, они не заметят. Если выкатывается новый формат дайджеста, а старые пробы продолжают проходить, набор говорит «всё хорошо», а читатели видят мусор.
- Они проверяют артефакты, а не замысел: дайджест с тремя карточками пройдёт, даже если карточки не про то.
- База — это снимок: после осознанного изменения поведения непринятая база покажет регрессию, которая на самом деле — решение. Дисциплина `accept` — единственное, что стоит между мной и базой, которая лжёт.
- Проба может проходить, когда мир сломан, и может падать, когда ничего не сломано. Набор — отбойник, а не гарантия.

## Структура каталога

```
18-harness-probes/
├── probes.py                     # прогон: run | check | accept | list
├── probes_check.sh               # обёртка для планировщика (молчит в норме)
├── examples/probe_set.example.json
└── tests/test_probes.py          # офлайн-тесты: свежесть, регрессия, секреты, разбор
```

`tests/test_probes.py` — это набор, которым я пользуюсь при разработке самого `probes.py`: он разворачивает временный `HARNESS_HOME` и прогоняет каждый вид пробы насквозь без настоящей обвязки. Он ловит «не сломал ли я детектор свежести?» и «не сломал ли я детектор регрессии?» до того, как я закоммичу. Он не заменяет прогона против настоящего `$HARNESS_HOME`; это проверка работоспособности, что раннер делает то, что обещает в строке документации.

## Развёртывание

Зависимостей, кроме стандартной библиотеки Python, нет. Запускать из любого планировщика: обёртка возвращает код возврата, поэтому подойдёт любой супервизор, понимающий ненулевой код. Целиком это один скрипт и один JSON-файл — и в этом весь смысл: минимальная вещь, которая может встать между правкой обвязки и продакшеном.

## Отказ от ответственности

Пробы уменьшают радиус поражения от правок обвязки, но не делают агента безопасным для работы без присмотра: каждый прогон ловит лишь то, что было записано в наборе, и не больше. Сканер секретов — эвристика против случайностей, а не средство защиты. Проба, которая сегодня проходит, не обещает, что та же проба пройдёт завтра; дисциплина `accept` после осознанного изменения поведения — на мне, а не на инструменте.
