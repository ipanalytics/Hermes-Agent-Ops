**«Задание отработало» — не то же самое, что «задание сделало работу», а трасса исключения — не диагноз.**

> Крон, который вышел с кодом 0 и ничего не доставил, выглядит ровно как тихая неделя. Отказ,
> повторяющийся ежедневно, выглядит как шум в логе. Этот каталог закрывает середину петли
> надёжности: проверки, которые убеждаются, что агент произвёл обещанный *результат*, и разбор,
> превращающий строку ошибки в класс и следующий шаг.

## Обзор

| Инструмент | Задача |
|---|---|
| `task_evals.py` | свежесть, размер и форма выводов, серии провалов, зависшие очереди — молчит в норме |
| `postmortem.py` | классифицирует последнюю ошибку, пишет журнал, сообщает о каждом новом падении ровно один раз |
| `briefing.py` | собирает открытые дела, свежие изменения, счётчики здоровья и неразобранные падения в короткий бриф, который читает задание |

## Как работает task_evals

Проверки описываются данными, а не кодом:

```json
{"id": "digest-cards", "kind": "output_fresh", "jobs": ["job-digest-morning"],
 "max_age_hours": 30, "min_bytes": 2000,
 "pattern": "^\\s*(?:№\\s*\\d+|\\d+)[).]?\\s", "min_hits": 3}
```

Полезнее всего `output_fresh`: последний вывод задания должен быть свежим, нетривиальным по размеру
и содержать структурные признаки обещания — три нумерованные карточки в дайджесте, заголовок в
отчёте. `no_failures` следит за сериями, а не за единичными ошибками: один отказ — совпадение, три —
закономерность. `queue_clear` запускает вашу команду очереди и считает зависшие элементы.

Код 0 и пустой вывод означают, что задания сделали обещанное; прогон по расписанию человек читает
только тогда, когда тот заговорит.

## Как работает postmortem

Пять классов, срабатывает первый подошедший: доставка, лимит модели, состояние/база, сеть, скрипт.
У каждого есть совет, поэтому отчёт — это следующий шаг, а не пересказ ошибки:

```
🩺 Разбор падений (автоматически):
  • стриминг-новинки [состояние/база]: session storage could not be written
    → проверить место и блокировки базы, затем health-check рантайма
```

Отпечатки разобранных падений хранятся, поэтому уже виденная проблема не повторяется каждый прогон:
журнал держит историю, отчёт — только новое. Это разница между потоком оповещений, который
отключают, и тем, который читают.

## Как работает briefing

Задания по расписанию стартуют с пустой головой. Восстанавливать контекст, перечитывая всё, стоит
одних и тех же токенов каждый прогон; собранный один раз короткий бриф стоит несколько сотен и
читается многими. Бриф берёт открытые дела, хвост журнала изменений, счётчики здоровья из
инструментов этой серии и неразобранные падения — и пишет туда, откуда задание читает его как
контекст.

## Быстрый старт

```bash
cp examples/task_evals.json .
python3 task_evals.py --jobs ~/.hermes/cron/jobs.json --output-dir ~/.hermes/cron/output \
    --config examples/task_evals.json --report ~/.hermes/data/task_evals.json
python3 postmortem.py --jobs ~/.hermes/cron/jobs.json
python3 briefing.py --config examples/briefing.json
```

## Ограничения

- Структурные проверки убеждаются в форме, а не в смысле: три карточки могут быть не теми тремя.
- Классификатор лексический; необычная ошибка попадает в «прочее» и сообщается как неопознанная —
  это честный исход.
- Бриф настолько свеж, насколько свежи файлы, которые он читает; устаревший источник даёт устаревший бриф.
