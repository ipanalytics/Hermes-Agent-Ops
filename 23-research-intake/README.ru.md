**Читать литературу как корпус, который я считаю, а не как ленту, которую листаю, — и вести журнал того, что я действительно внедрил.**

Hermes — мой домашний ИИ-агент, небольшая программа, которая живёт на моём собственном сервере. Она выполняет задания по расписанию — повторяющиеся дела, срабатывающие в заданное время (каждое утро, каждый час, каждый понедельник в 09:00 — примерно как напоминание в календаре, только вместо уведомления запускается скрипт) — и берёт на себя рутину без моего участия: ежедневный дайджест, наблюдение за ценами, сводку по здоровью, проверку, что собственные службы агента всё ещё живы. К исследованиям большинство этих заданий отношения не имеет. Эта папка — то, что имеет. Здесь живёт фиксированный способ выкачивать категорию статей из публичного архива, считать одни и те же слова в одном и том же тексте неделя за неделей и записывать то, что я в итоге изменил в работе. Парный модуль 27 (`research-scout`) ищет конкретные ответы на конкретные вопросы; этот — измеряет дрейф целых категорий и кладёт результат в журнал, который я читаю каждый понедельник.

Большинство «трендовых» отчётов сравнивают то, что индекс показал на этой неделе, с тем, что он показал на прошлой: каждый раз другая выборка, поданная как направление. График движется из-за того, что поисковик передумал, а не из-за того, что изменилась область. Эта папка идёт другим путём. Я выкачиваю фиксированный набор работ по протоколу харвестинга — способу скачать всё из категории целиком прямо из архива, вместо вопросов поисковику по одному, — считаю слова локально в равных окнах и храню каждую идею, пережившую неделю, в журнале с первым шагом, метрикой и датой отсечения.

## Зачем это нужно

Поисковый API отвечает на вопрос «что индекс считает релевантным», по одной странице, с лимитами, не имеющими отношения к моему профилю использования. Я измерил это напрямую: API запросов arXiv возвращал ошибку лимита даже на тривиальный запрос из одного термина, причём с двух разных сетей — то есть ограничение не по IP и ротацией выхода (внешнего сетевого маршрута моего трафика) не лечится. У протокола харвестинга (OAI-PMH, Open Archives Initiative Protocol for Metadata Harvesting — небольшой аккуратный стандарт XML поверх HTTP, который позволяет клиенту пройти весь архив по порядку, страница за страницей, с закладкой «продолжить отсюда») замысел противоположный. `ListRecords` с набором и токеном продолжения — закладкой, которую сервер возвращает, чтобы следующий вызов продолжил с места остановки предыдущего, — обходит весь набор, по одному запросу за раз. OAI-эндпоинт arXiv отдавал тысячи записей в неделю там, где API запросов не отвечал вовсе. Три секунды между запросами — часть договорённости; один запрос за раз, каждый раз — цена корпуса, который не зависит ни от чьего ранжирования.

Подсчёт затем идёт локально, по выкачанному тексту, моими регулярными выражениями (regex — небольшие шаблоны поиска слов или форм слов в тексте):

```bash
python3 oai_harvest.py --set cs:cs.AI --days 7 --out data/cs.AI.jsonl
python3 oai_harvest.py --count data/cs.AI.jsonl --terms examples/terms.json
```

Именно это делает сравнение по неделям честным: одна и та же форма корпуса, одни и те же шаблоны, без меняющегося под низом ранжирования. Доли печатаются вместе с числом записей, потому что неделя с удвоенным числом записей раздувает любое абсолютное значение. Если бы я написал «X вырос на 30%», не сказав читателю, что корпус заодно удвоился, я построил бы график, а не измерение.

## Журнал

| Файл | Задача |
|---|---|
| `oai_harvest.py` | пройти набор OAI-PMH с токеном продолжения, дописать JSONL, посчитать термины офлайн |
| `direction_digest.py` | доли терминов по равным окнам, сдвиг помечается только если пережил сравнение |
| `backlog.md` | схема журнала и правила, не дающие ему превратиться в музей |

`backlog.md` описывает схему, которую я держу рядом с корпусом. Каждая идея, пережившая неделю чтения, должна быть записана с этими полями:

- `id` — короткое имя, по которому удобно искать. Строчные буквы, дефисы, стабильное при правках.
- `source` — откуда пришла (идентификатор arXiv, ссылка на пост, разговор в коридоре). Без источника «я где-то это читал» становится нормой, и идею нельзя перепроверить.
- `found` — дата, когда я её заметил. Без даты нормой становится «я это уже несколько лет обдумываю», и ничто никогда не сдвигается.
- `status` — одно из четырёх: `candidate` (заметил, ничего не пробовал), `trying` (первый шаг идёт и часы тикают), `adopted` (изменило рутину агента), `rejected` (пробовал, метрика не двинулась, вот почему).
- `first_step` — минимальное действие, которое можно сделать на этой неделе. Если не могу назвать — это заметка, а не кандидат.
- `metric` — число, по которому понятно, сработало ли. «Лучше» — не метрика.
- `kill_by` — дата, после которой я перестаю ждать. После неё запись становится отказом с причиной.
- `reason` — обязательно для `rejected`, стоит заполнять и для остальных. «Пробовал, метрика не двинулась» — самая переиспользуемая строка файла.

Два правила из `backlog.md` делают основную работу:

- **Равные окна, доли вместо абсолютов** — иначе загруженная неделя читается как тренд.
- **У отказов остаётся причина** — «пробовал, метрика не двинулась» самая переиспользуемая строка в файле и единственное, что не даёт одной и той же идее возвращаться каждый квартал.

Ещё три правила, выученные на своих ошибках и тоже живущие рядом со схемой в `backlog.md`:

- **Нет теории без первого шага.** Запись, которая не может назвать минимальное действие, — заметка.
- **Один кандидат за раз в каждой области, с откатом.** Два одновременных изменения в одной части системы потом нельзя атрибутировать: если метрика двинулась, я не знаю, какое из двух её сдвинуло.
- **Скрипт лучше модели.** Если шаг можно сделать детерминированным, он перестаёт конкурировать за внимание и бюджет с шагами, которым действительно нужно суждение.

## Быстрый старт

```bash
cp examples/terms.json .
python3 oai_harvest.py --fixture examples/oai_fixture.xml --out data/example.jsonl   # офлайн-проверка
python3 oai_harvest.py --set cs:cs.AI --days 7 --out data/cs.AI.jsonl
python3 oai_harvest.py --count data/cs.AI.jsonl --terms examples/terms.json
python3 direction_digest.py --corpus data/cs.AI.jsonl --terms examples/terms.json --weeks 5 --out digest.md
```

Первый запуск офлайновый: сохранённый ответ из `examples/oai_fixture.xml` разбирается без сети, и я вижу, что мои регулярки и работа с датами в порядке, прежде чем тратить запрос на живой архив. Третий запуск обходит набор arXiv `cs.AI` за последние семь дней и дописывает по одной JSON-записи на работу в `data/cs.AI.jsonl`. Четвёртый печатает счётчики и доли. Пятый делит корпус на равные по времени корзины и пишет дайджест, в котором помечаются только сдвиги больше одного процентного пункта — более мелкие движения получают знак равенства, потому что на выборке такого размера это в основном шум.

## Что на выходе

- Файл JSONL на набор — по одному JSON-объекту на строку (JSON Lines: каждая строка — самостоятельная JSON-запись), одна строка на скачанную работу, с идентификатором, заголовком, аннотацией, датой создания и темами. Простой текст, построчный формат, легко grep'ать, легко переобработать, легко расширить.
- Счётчики по терминам и доли по неделям, напечатанные вместе с числом записей — чтобы читатель видел и абсолютный счётчик, и долю, и замечал, когда доля выросла из-за роста термина, а не из-за роста корпуса.
- Дайджест, помечающий только сдвиги, пережившие сравнение равных окон, и запись в журнале с первым шагом, метрикой и датой отсечения для каждой идеи, которую я решил пробовать.

## Ограничения

- Наборы пересекаются, записи объявляются повторно; дедупликация по идентификатору закрывает общий случай, но не каждое перекрёстное попадание. Если работа лежит в двух категориях, она появится в моих счётчиках дважды, и с этим приходится жить, пока я не начну объединять по каноническим идентификаторам. Я выбираю прозрачность ценой полноты: любая дедупликация, скрывающая запись, скрывает её и от меня.
- Подсчёт терминов измеряет лексику, а не качество. Термин может вырасти потому, что больше работ используют это слово в аннотации, и по счётчику нельзя понять, есть ли среди этих работ что читать. Счётчик подсказывает, куда смотреть; чтение показывает, что там.
- OAI-PMH вежлив по замыслу: полный обход набора занимает минуты и несколько запросов, с трёхсекундной паузой между вызовами. Это цена стабильного корпуса, и при одном прогоне в неделю она мала. Полный обход `cs.AI` за последние семь дней укладывается в минуту на моей линии; крупные наборы (`cs` целиком) занимают несколько минут и хорошо запускаются на ночь.
