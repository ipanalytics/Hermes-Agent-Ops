Каждое утро мои агенты кладут мне на стол несколько дайджестов — коротких сводок за прошедший день: что
двигалось на рынках, что поезд сделал с моим расписанием, какую запись про пептиды стоит перечитать
второй раз, что нового на arXiv. По отдельности ни один из них не звучит как срочность, и в этом сама
проблема: когда один из них тихо перестаёт приходить, я не чувствую дыры. Просто одним меньше пунктом
для чтения в это утро. Через две недели я, может быть, замечу. К тому моменту я уже пропустил серию
релизов, падение цены или статью, которая изменила бы моё утро.

Эта папка — скрипт, который ловит ту тишину рано. Он читает журнал аудита — JSONL-файл, где каждый
запуск cron-задачи оставляет однострочный след: метка времени, id задачи, ответил ли агент содержимым,
была ли ошибка, сколько заняло, — и сравнивает то, что реально сработало, с тем, что по расписанию должно
было сработать. Разница между ними и есть моё «здоровье доставки».

Cron-задача, для тех, кто с термином не знаком, — это поручение, которое операционная система сама
запускает по расписанию, без клика по «выполнить». Агент, в том смысле, в каком я тут употребляю это
слово, — одна из таких задач, которой рулит языковая модель: маленький скрипт на Python, который просит
модель собрать дайджест и кладёт результат туда, где я его прочту. Ворот (он же gateway) — небольшой
сервис перед ними всеми: через него ходит трафик агентов, по нему идёт cron-расписание, и он же пишет
журнал аудита после каждого запуска. У меня несколько десятков cron-задач. Часть ежедневно, часть только
по будням, часть только по понедельникам, часть только по субботам. Смесь важна: пропущенная
понедельничная задача невидна до следующего понедельника, а пропущенная ежедневная невидна, пока кто-то
случайно не вспомнит, что она вообще существует. Мне нужна была одна страница, которая каждое утро
говорила бы, какие из моих каналов перестали работать, — без того, чтобы открывать девять почтовых
клиентов и считать.

## Зачем это нужно

Толчком стал один пропущенный утренний дайджест. Он должен был лечь в 06:00, и во вторник не лёг, а в
среду я был занят, и в четверг я списал вторник на глюк, а в пятницу открыл инбокс на стопке новостей,
которые хотел бы получить в понедельник. Задача умерла за пять дней до этого — путь в промпте был
переименован во время рефакторинга, и агент молча упал с ошибкой «нет такого файла», которую посчитал
безобидной. Никакого оповещения не сработало, потому что журнал аудита в вороте записывает только то,
что задача запустилась; он не записывает, что запуск довёл до меня что-то полезное.

К тому моменту, как я сел чинить, такая же дыра уже стоила мне понедельничного дайджеста по пептидам
(заметил, когда записи в моих заметках перестали прибавляться) и тихого weekend-роллапа релизов
(заметил только потому, что коллега спросил, почему я не обсуждаю шоу, которое у всех на слуху). За одну
неделю набралось три независимых тихих сбоя, и единственным общим фактом было то, что про каждый из
них я узнал случайно.

Починить это словами «каждый день читать логи руками» было нельзя — я бы перестал их читать руками
уже через две недели. Починить это нужно было скриптом, который делает за меня скучную часть, который
сам живёт в cron, чтобы проверка не зависела от моей памяти, и который выдаёт отчёт, на который я
могу глянуть за пятнадцать секунд. Это и есть `digest_health.py`.

Ещё один урок из того случая: покрытие никогда не бывает одной цифрой. Неделя тишины для ежедневного
дайджеста — инцидент. Та же неделя тишины для еженедельного — норма. Скрипт, который усреднит всё в
одно число, будет либо кричать еженедельно, либо молчать ежедневно. Я выдаю отчёт по каждому каналу
отдельно, со своим зелёным/жёлтым/красным, и даю тренду по неделям ловить медленные сползания, которые
одна сводка за неделю не покажет.

## Как это работает

1. Скрипт открывает `~/.hermes/cron/jobs.json` и достаёт оттуда текущий каталог задач. У каждой записи
   есть id, человеческое имя и расписание. Если файл потерян или битый, скрипт откатывается на свой
   собственный встроенный список известных дайджестов и идёт дальше — ухудшенный отчёт лучше, чем
   никакого.
2. Открывает журнал аудита по пути `~/.hermes/cron/usage_audit.jsonl` — по одному JSON-объекту на строку,
   который ворота дописывают после каждого запуска. Парсит каждую строку, выбрасывает нечитаемые и
   оставляет только записи, попавшие в последние семь полных суток по UTC (текущий день ещё не закончился
   и не считается).
3. По каждому известному дайджесту считает, сколько раз за это окно он должен был сработать: ежедневный
   ждёт семь запусков, понедельничный — количество понедельников в окне, будний — пять, субботний —
   один. Это ожидаемое число и есть контракт расписания; журнал аудита хранит то, насколько этот контракт
   реально соблюдался.
4. По каждому дайджесту затем считается покрытие как `actual / expected`, считаются запуски, пришедшие
   молча (агент вернул пустой ответ), считаются запуски с ошибкой и запоминается самое долгое одиночное
   выполнение в окне. Покрытие ниже 80% или любая ошибка переводят строку в красный; покрытие ниже 100%
   держит её в жёлтом; полное покрытие без ошибок делает её зелёной.
5. Скрипт читает снимок прошлой недели из `~/.hermes/data/digest_health_state.json` и к строкам, у которых
   покрытие хуже прошлой недели, дописывает маленькую стрелку вниз. Стрелка — самая дешёвая часть
   отчёта и та, которой я доверяю больше всего: один жёлтый, который портится три недели подряд, — это
   сигнал, который один жёлтый сам по себе не поднимет.
6. Результат целиком уходит в stdout, а новый снимок атомарно записывается в state-файл — сначала в
   `digest_health_state.json.tmp`, затем переименовывается на место через `os.replace`, так что крэш
   посреди записи не оставит полузаписанный state-файл, который следующий запуск прочитает как истину.
   Строка в stdout — это то, за что держится мой cron gate (внешняя проверка, которая смотрит на вывод
   скрипта и поднимает тревогу, когда вывод меняется или пропадает), если я захочу поднимать эскалацию
   на красном.

Сам скрипт запускается из cron. Мониторинг, который требует, чтобы я помнил его запустить, — это не
мониторинг.

## За какими дайджестами я слежу

Скрипт сейчас знает девять дайджестов по id и короткому имени; расписание зашито прямо в файл маленькой
лямбдой на каждый дайджест. Это список, который есть у меня сегодня; файл короткий специально, и я
правлю его, когда добавляю новый.

| Короткое имя | Ожидается за 7 дней |
|---|---|
| `morning-releases` | 7 (ежедневно) |
| `weekday-day-releases` | 5 (пн–пт) |
| `weekend-releases` | 2 (сб–вс) |
| `morning-train` | 5 (пн–пт) |
| `ai-digest` | 7 (ежедневно) |
| `peptides-mon` | количество понедельников |
| `gene-digest` | 7 (ежедневно) |
| `streaming-mon` | количество понедельников |
| `expense-sat` | количество суббот |

Ожидаемые количества считаются в UTC — это часовой пояс, в котором работает мой ворот и в котором
написаны мои cron-расписания. В другом часовом поясе числа нужно переводить, прежде чем они что-то
значат.

## Быстрый старт

```bash
# Установите необходимые переменные окружения
export HERMES_AUDIT_LOG=~/.hermes/cron/usage_audit.jsonl
export HERMES_JOBS_FILE=~/.hermes/cron/jobs.json
export HERMES_DIGEST_HEALTH_STATE=~/.hermes/data/digest_health_state.json

# Запустите скрипт
python3 digest_health.py
```

Скрипт не принимает аргументов командной строки. Всё, что я хочу крутить, — список дайджестов, пороги
покрытия, порог медленного запуска в 120 секунд — лежит константами в начале файла. Я пока не вынес
это в конфигурацию, потому что у меня нет второго развёртывания; такой рефакторинг окупается, только
когда где-то работает второй экземпляр скрипта.

## Что на выходе

Короткий markdown-отчёт, напечатанный в stdout. Строка выглядит как `<свет> <имя>: <факт>/<ожид>`, а
после неё дописываются `silent N`, `errors N` или `slow N s`, когда эти числа ненулевые, и стрелка
вниз, когда покрытие за эту неделю хуже прошлой. Свет — красный для строки с ошибками или покрытием
ниже 80%, жёлтый для покрытия ниже 100%, зелёный иначе.

Под таблицей, когда хотя бы одна строка жёлтая или красная, скрипт дописывает напоминание
`There are gaps — see last_error/check, fix if repeated for 2+ days.` Один жёлтый — ещё не инцидент;
тот же жёлтый на второй день подряд — уже.

State-файл по пути `~/.hermes/data/digest_health_state.json` хранит снимок прошлой недели — начало
недели, по каждому дайджесту ожидаемое/фактическое/молчания/ошибки/покрытие. Это единственное
состояние, которое держит скрипт, и файл перезаписывается атомарно при каждом запуске.

## Ограничения

- Скрипт доверяет формату журнала аудита. Битая строка выбрасывается молча, и запуск того дня пропадает
  из отчёта. Число отброшенных строк в собственном логе ворота я держу как отдельный сигнал.
- Вся арифметика по окнам работает в UTC. Переходы на летнее/зимнее время в моём локальном поясе не
  двигают границы семидневного окна, и это то, чего я хочу.
- Список известных дайджестов зашит в скрипт. Десятый дайджест означает правку файла; если я добавлю
  новую cron-задачу и забуду дописать её сюда, она останется невидимой для проверки, пока я сам не
  замечу. Я держу эту петлю короткой, потому что цена забывчивости — ровно та тишина, которую скрипт
  и должен ловить.
- Исторический анализ смотрит только на две соседние недели. Долгое сползание за месяц будет видно
  как «эта неделя хуже прошлой», пока тренд не догонит; это сознательное решение — длинная история
  живёт в `BENCHMARKS.md`.
- State-файл хранит снимок прошлой недели, а не полную историю. Удалить его можно: следующий отчёт
  просто выйдет без стрелки тренда.

## Структура

- `digest_health.py` — сам скрипт
- `tests/test_digest_health.py` — модульные тесты на вспомогательную функцию подсчёта будней
  (`_weekdays`)
- `examples/jobs.json` — крошечный пример каталога задач с двумя записями, которого хватает, чтобы
  прогнать путь загрузки
- `examples/usage_audit_sample.jsonl` — одна примерная запись аудита с теми полями, которые читает
  скрипт (`ts`, `job_id`, `response_silent`, `error`, `duration_ms`)
- `README.md` — этот файл по-английски
- `README.ru.md` — этот же файл по-русски
