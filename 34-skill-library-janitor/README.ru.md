# 34 — skill-library-janitor

_English version: [README.md](README.md)_

**Библиотека скиллов не ломается громко. Переименованный файл, скрипт, который перестал
компилироваться, поле описания, которое потерялось — всё это выясняется посреди работы, когда
скилл загружается, а пути, который ему нужен, уже нет.**

> Ничего хитрого здесь нет: инструмент обходит библиотеку и сообщает только то, что проверяемо
> неверно. В этом и смысл. Месячный прогон ничего не стоит, модель не вызывается, а целый класс
> тихого гниения превращается в короткий список, с которым можно что-то сделать. Формулировки,
> тон и полезность — не его дело.

## Что вы получаете

- `janitor.py` — обходит каждый `SKILL.md` под одним или несколькими корнями и сообщает о битых
  ссылках, не компилирующемся коде и проблемах с полем описания. Готов к крону: `--quiet`
  молчит, когда библиотека чистая.
- `examples/sample-library/` — библиотека из трёх скиллов (один чистый, один со старыми
  ссылками, один с синтаксической ошибкой) и записанный отчёт, который инструмент для неё даёт.
- `tests/test_janitor.py` — 11 офлайн-тестов, собирающих одноразовые библиотеки во временном
  каталоге.

## Что проверяется

| Проверка | Что ловит | Почему это важно |
|---|---|---|
| Поле описания | нет `name`/`description`, описание вне 20–200 символов, `name` разошёлся с каталогом | по описанию загрузчик подбирает скилл под задачу; разошедшееся имя ломает поиск |
| Ссылки на файлы | `~/...`, абсолютные пути и упоминания `scripts/foo.py`, которых больше нет | скилл загружается, а падает ровно в тот момент, когда понадобился |
| Синтаксис Python | файлы внутри скилла, которые больше не компилируются | обновление интерпретатора или плохая правка не видны до запуска |
| Синтаксис shell | `.sh`-файлы, не проходящие `bash -n` | то же самое, на шаг раньше |

## Как пользоваться

```bash
python3 janitor.py --skills-dir ~/.hermes/skills --report janitor.json

# крон / месячная задача: молчит, когда чисто; ненулевой код выхода, когда грязно
python3 janitor.py --skills-dir ~/.hermes/skills --quiet --strict
```

`--skills-dir` принимает несколько корней. `--home` задаёт, во что раскрывается `~/` (удобно в
тестах и для библиотек вне домашнего каталога). `--no-code` пропускает компиляцию — быстрый
проход только по описанию и ссылкам.

## Выходные данные

```
$ python3 janitor.py --skills-dir examples/sample-library/skills --home examples/sample-library/home
skill library: 3 checked, 2 need attention (paths outside this machine, not counted as broken: 0)
- examples/sample-library/skills/endpoint-check: missing path: ~/.config/endpoints.json; missing script: legacy_ping.sh
- examples/sample-library/skills/weekly-report: collect.py: syntax error at line 4
```

`--report FILE` записывает тот же результат в JSON с отметкой времени, чтобы месячная задача
оставляла след о том, что она видела, а не только о том, жаловалась она или нет.

## Калибровка, чтобы отчёт оставался осмысленным

- `scripts/foo.py` в скилле обычно означает общий каталог скриптов библиотеки, а не папку внутри
  скилла. Прежде чем объявить ссылку битой, проверяются три места; объявлять их битыми по
  умолчанию — это способ сделать санитара проигнорированным.
- Пути с заглушками (`<name>`, `*.py`, `$VAR`, `~/.cache/…`) пропускаются: это шаблоны, а не
  артефакты.
- Путь, которого нет вне домашнего дерева, считается, но не перечисляется — такие обычно
  принадлежат другим машинам и другому софту, это документация, а не гниение.
- Не больше шести замечаний на скилл, чтобы один сломанный скилл не похоронил остальные.

## Ограничения

- Инструмент судит только то, что проверяемо. Скилл с неверными указаниями, но живыми путями —
  проходит.
- Проверка Python — только синтаксис: импорты, отсутствующие зависимости и мёртвые эндпоинты вне
  области. Она не ходит в сеть.
- Эндпоинт, который отвечал в прошлом месяце и умер сегодня, — не её дело; и она не скажет, что
  ночное обновление зависимостей сломало то, что всё ещё компилируется.
- Запускать по расписанию. Санитар, прошедший один раз, ничего не доказывает о следующих месяцах.
