# Hermes Agent Ops

Операционные паттерны, инструментарий и записи об инцидентах для запуска LLM-агентов в качестве сервиса 24/7. Репозиторий охватывает ограничители расходов (spend guards), внешний надзор за процессами, архитектуру профилей с несколькими ролями, самонаблюдающиеся запланированные задания и post-mortem-разборы, стоящие за каждым компонентом. Всё здесь обобщено на основе продакшн-развёртывания, которое работает круглосуточно, — каждый артефакт представляет собой либо исполняемый код, либо шаблон конфигурации, опробованный в той среде.

Основная цель — [Hermes Agent](https://hermes-agent.nousresearch.com); паттерны и большая часть инструментария применимы к любому агентному шлюзу с планировщиком, хранилищем состояния и API провайдеров.

## Обзор

На четыре режима отказа приходится большая часть простоев и расходов агентов:

- одна сессия разрастается, пока не начинает доминировать в расходах и качестве ответов,
- процесс шлюза продолжает работать, но отказывается принимать новые записи,
- запланированные задания дрейфуют или тихо умирают,
- задокументированное расписание расходится с фактическим.

Каждый из них обрабатывается компонентом с определённым правилом обнаружения и путём реагирования:

- расходы привязаны к балансу провайдера и атрибутируются по сессиям,
- работоспособность процесса оценивается по heartbeat *и* маркерам фатальных ошибок в журнале, причём извне шлюза,
- каждый запланированный промпт проверяется на самодостаточность перед отправкой,
- эксплуатационная документация генерируется из списка заданий, а не ведётся вручную.

Семнадцать модулей в пронумерованных каталогах, каждый читается самостоятельно, с перекрёстными ссылками в `SERIES.md`.

## Архитектура

```
                        ┌──────────────────────────────┐
   human (DM/topics) ──▶│  gateway + role profiles      │◀── SOUL.md per role
                        │  coordinator · chef · doctor  │    model pinning
                        │  operator (3rd model)         │    topic walls
                        └──────────────┬───────────────┘
                                       │ state DB + logs + heartbeat file
        ┌──────────────┬───────────────┼────────────────┬────────────────┐
        ▼              ▼               ▼                ▼                ▼
   scheduler      gateway           wallet guard     usage DB        backups
   (cron jobs)    supervisor        (every 30 min)   (sqlite)        (daily)
      │           (external)            │
      │           + guard cron          ▼
      ▼                           cost dashboard
   no-agent watchers              (attribution)
   LLM digests (gated)
   one-shot reminders
```

Три свойства выполняются на каждом уровне:

1. **За наблюдателями следит другой уровень — не тот, за которым следят они сами.** Шлюз находится под надзором внешнего демона; демон заново запускается guard-cron'ом, принадлежащим планировщику; само расписание аудируется ежедневным операторским обходом, выполняющимся на отдельной модели.
2. **Молчание — валидное состояние.** Наблюдатели ничего не выводят, пока всё в порядке; планировщик ничего не доставляет при пустом stdout.
3. **Ничто не исцеляется изнутри.** Пути перезапуска, восстановления и эскалации находятся вне шлюза, и состояние никогда не восстанавливается автоматически роботом.

## Возможности

| Модуль | Ответственность |
|---|---|
| `01-agent-wallet-guard` | Напрямую измеряет баланс провайдера; сигнализирует о пробитии нижнего порога и о дневном расходе, называя сессию-лидера по токенам чтения кэша (cache-read tokens). Молчит при нормальном состоянии. |
| `02-agent-gateway-supervisor` | Внешний демон в виде **systemd user unit** (не cron-страж): устаревание heartbeat + свежие маркеры фатальных ошибок в логах; перезапуск только через `systemctl` (polkit-разрешение); cooldown + почасовой лимит; пауза на обслуживание; эскалация вместо автовосстановления. |
| `03-agent-ops-playbook` | Обезличенные разборы инцидентов и деревья решений для повторяющихся классов отказов. |
| `04-role-profiles` | Шаблон мастер-промпта SOUL.md, закрепление модели/конфигурации за каждой ролью, файловые мосты между ролями. |
| `05-cron-of-crons` | Бриф обхода оператора, матрица «кто за кем следит», политика доставки дайджестов, алертов и разовых задач (one-shot). |
| `06-hermes-plugins-skills` | Упакованный skill (разовое напоминание) и рецепты cron: дайджесты с гейтом от монитора, цепочки watchdog. |
| `07-fresh-prompt-linter` | Детерминированная проверка самодостаточности промпта; гейт для запланированных промптов перед деплоем. |
| `08-session-housekeeping` | Правила жизненного цикла сессий/памяти/skill-ов и задачи консолидации. |
| `09-ops-as-data` | Экспортёр, формирующий таблицу наблюдения из списка задач планировщика. |
| `10-cost-dashboard` | HTML-панель в одном файле: расходы по дням, провайдерам и ведущим сессиям. |
| `11-domain-persona-packs` | Ролевые картриджи для `04`: повар с инвентарём, врач с файлом лимитов, оператор. |
| `12-topic-routing` | Изоляция топиков как доменов, стены ignore-списков, маршрутизация алертов в личные сообщения (DM). |
| `13-voice-input-hypotheses` | Защита от искажений транскрипции: имена, полученные голосом, — гипотезы, пока не сверены с эталонными данными (ground truth). |
| `14-agent-data-intake` | Надёжный приём данных от устройств агентом: многопоточный приёмник в виде systemd user unit (никогда не cron шлюза), spool на стороне устройства с повторными попытками до доставки, сканирование 24/7 без временных окон. |
| `15-agent-tool-guardrails` | Оценка извне, применяемая к командам и worktree: гейт `pre_tool_call` на основе AST (не regex по строке), сканер skill-ов на инъекции/эксфильтрацию до того, как установке будет оказано доверие, и дорожки git-worktree, карточки которых закрываются по доказательствам, созданным оркестратором. |
| `16-gepa-skill-tuner` | Рефлексивная эволюция промптов (GEPA), нацеленная на артефакты, которые агент реально поставляет, — промпт и SKILL.md — с заявленным бюджетом метрик, дедуплицированным датасетом, отложенной выборкой (held-out) и diff в качестве результата. |
| `17-model-slot-bakeoff` | Подбирает модель для слота, измеряя реальные задачи этого слота: тарифицируемая стоимость на задачу, задержка, апстрим, который реально обслуживал, оценка на скрытом тесте и поддержка tool-call. |

## Быстрый старт

Склонируйте репозиторий и начните с модуля, соответствующего вашей текущей проблеме:

```bash
git clone <this-repository> hermes-agent-ops
cd hermes-agent-ops

# spend watch: point the guard at your provider balance endpoint
cd 01-agent-wallet-guard
export WALLET_API_KEY=sk-...
python3 agent_wallet_guard.py            # silent when healthy
```

`15` поставляется с тестами (`tests/`) и требует один pure-python wheel (`bashlex`, включён в состав его установщика). Страж, супервизор, линтер, экспортёр и дашборд используют только стандартную библиотеку Python 3.10+ — без установки зависимостей. Шаблоны и промпт-брифы в остальных модулях используются как есть.

## Установка

- **Python**: 3.10+; для всех поставляемых инструментов — никаких сторонних пакетов (сетевые вызовы через `urllib`, рендеринг — простой HTML, состояние — JSON).
- **Опциональное хранилище данных**: таблица использования sqlite для атрибуции по сессиям (схема ниже). Без неё страж продолжает подавать алерты; он просто не может назвать сессию-виновника.
- **Транспорт**: наблюдатели пишут в stdout (доставку осуществляет планировщик), супервизор общается с Telegram через Bot API, используя токен из окружения. Доставка — забота планировщика.

Запланированные компоненты предназначены для запуска следующим образом:

```
every 30 min   → 01 wallet guard            (no-agent job, stdout → alert topic)
every 5 min    → 02 supervisor guard cron   (re-spawn daemon if dead)
continuous     → 02 supervisor daemon       (setsid, detached)
0 5 * * *      → 05 operator sweep          (LLM job, third model)
daily 11:00    → 09 exporter → commit       (docs generation)
```

## Примеры использования

Проверьте запланированный промпт линтером перед его отправкой:

```bash
python3 07-fresh-prompt-linter/fresh_prompt_linter.py --prompt-file brief.md
echo $?   # 0 = deploy, 1 = make it self-contained first
```

Сформируйте таблицу наблюдения из списка задач:

```bash
python3 09-ops-as-data/cron_exporter.py \
  --jobs jobs.json --out WATCH-TABLE.md
```

Сгенерируйте панель расходов:

```bash
python3 10-cost-dashboard/cost_dashboard.py \
  --db /var/lib/agent/state.db --days 14 --out cost-dashboard.html
```

## Форматы данных

Общая sqlite-таблица использования (заполняется системой учёта использования шлюза, читается `01` и `10`):

```sql
CREATE TABLE session_model_usage (
  session_id        TEXT,
  billing_provider  TEXT,
  first_seen        INTEGER,   -- unix epoch
  cache_read_tokens INTEGER,
  input_tokens      INTEGER,
  output_tokens     INTEGER,
  reasoning_tokens  INTEGER,
  api_call_count    INTEGER
);
```

Список задач планировщика, потребляемый экспортёром (`09-ops-as-data/jobs.example.json`):

```json
{
  "id": "ab12cd34",
  "name": "morning train digest",
  "schedule": "0 6 * * 1-5",
  "agent": true,
  "deliver": "topic: commutes",
  "notes": "Mon-Fri only; deviations only, silence when on schedule",
  "watcher": "operator"
}
```

Файл состояния guard'а (JSON, по одному на хост): баланс якоря дня, временные метки троттлинга оповещений, последний наблюдаемый баланс. Пополнение заново привязывает день, так что пополнения не засчитываются как расход.

## Примечания по эксплуатации

- **Временные якоря — UTC.** Cron-выражения и одноразовые (one-shot) метки времени записываются в UTC; бриф оператора и примеры предполагают развёртывание в Europe/Berlin.
- **Компакция прежде стоимости.** Сессии ужимаются при пороге, достаточно низком, чтобы сбойная компрессия не могла нагнать часы платных повторов (разбор в `03/incidents/530k-token-session.md` — референсный случай).
- **Вспомогательные вызовы относятся к дешёвому провайдеру.** Вызовы компрессии, генерации заголовков и ревью доминируют в расходе токенов; закрепление их вне основного провайдера — бюджетное решение, а не оптимизация.
- **Резервные копии — прежде восстановления.** Бэкапы БД состояния выполняются ежедневно и хранятся ~1–2 дня; путь восстановления в `02` перед восстановлением помещает данные в карантин и никогда не удаляет повреждённую копию.
- **Исключения документируются для каждого развёртывания** (например, роль повара, освобождённая от сверки оператора). Это конфигурационное решение, а не недосмотр.

## Объём проекта

В рамках проекта: наблюдаемость (observability) и учёт расходов для трафика агентов, внешний надзор за процессами шлюза, управление жизненным циклом ролей и сессий, документация планировщика, гигиена промптов и runbook'и по инцидентам. Вне рамок: обучение моделей, маркетплейсы контента промптов и само ядро Hermes Agent — этот репозиторий работает *вокруг* шлюза, а не модифицирует его.

## Сценарии использования

- Развёртывания с одним шлюзом, несколькими профессиональными ролями и жёсткими бюджетными потолками.
- Команды, выполняющие LLM-задачи по расписанию, которым нужны документация, контрольные точки (gates) и цепочка наблюдения, прежде чем доверять им работу без присмотра.
- Операторы, унаследовавшие развёртывание агента, которым история инцидентов и деревья решений нужны больше, чем ещё одна архитектурная диаграмма.

## Ограничения

- Промпт-линтер эвристичен: он отмечает нарушения самодостаточности с высокой полнотой (recall), но прохождение линтера не доказывает, что промпт сработает.
- Дашборд стоимости оценивает по прайсовым ценам (list prices) для атрибуции; wallet guard измеряет фактические балансы как факт. Никогда не выставляйте счета на основе оценки.
- Поставляемые примеры используют Telegram-топики и Bot API как референсный транспорт; контракт guard'а и watchdog'а — stdout, поэтому другие транспорты не требуют изменения кода в watcher'ах.
- Отчёты об инцидентах обезличены: детали, по которым можно идентифицировать оператора или инфраструктуру, удалены.

## Развёртывание

Референсная компоновка для одного хоста:

1. **Шлюз + профили ролей** согласно `04`; состояние и логи в одном каталоге, доступном супервизору для чтения.
2. **Задачи планировщика** согласно `05`: наблюдатели на коротких интервалах, дайджесты по собственному расписанию, операторский обход — раз в сутки.
3. **Демон супервизора** запускается отсоединённо (`setsid`), перезапускается его сторожевым cron'ом — его PID, как ожидается, завершается вместе с перезапусками шлюза.
4. **Задача резервного копирования** для БД состояния, ежедневно, хранение ~1–2 дня.
5. **Сторож кошелька** — каждые 30 минут, ключ берётся из переменных окружения, в коммиты никогда не попадает.

Минимально жизнеспособное развёртывание состоит из двух компонентов: сторожа кошелька и пары супервизор + сторож. Плейбук — только для чтения; остальные модули добавляют роли, документацию и указание авторства по мере роста развёртывания.
